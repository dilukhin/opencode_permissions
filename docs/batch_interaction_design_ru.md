# Пакетное взаимодействие пользователя с OpenCode: вопросы и разрешения

Статус: **Q0 принят пользователем 13.10.2026**; A0 принят как проектное направление. Способ реализации не считается внедрённым или доказанным. Q1 проверяется отдельным [стендом](batch_questions_q1_probe_ru.md); A1 сохраняет собственные условия перехода.
Владелец задачи: [#48](https://github.com/dilukhin/opencode_permissions/issues/48).
Базовые ограничения: [default threat model](default_threat_model_ru.md), [архитектурная минимальность](architecture_simplicity_reconciliation_ru.md), [состояние проекта](STATUS.md).

## 1. Что решаем

Главная метрика проекта — число **прерываний пользователя**, а не просто число shell-диалогов. Пользователь должен один раз описать задачу, по возможности ответить на подготовленный пакет существенных вопросов и затем оставлять агента работать без вмешательства до реальной границы полномочий, неожиданного состояния или существенной новой неопределённости.

Различать:
- **Q / рабочий вопрос** — выбор целей, предпочтений или требований. Ответ меняет план, но сам по себе **не даёт разрешения на исполнение**.
- **A / техническое согласие** — подтверждение точно обозначенной операции, которая не получила автоматического `ALLOW`. Требует отдельного, доверенного канала решения и привязки к фактическому исполнению.
- **D / запрет** — технический `DENY`; пакет, модель-аудитор и подтверждение не должны его отменять.
- **E / событие работы** — уведомление/отчёт о выполненном безопасном шаге, которое не требует от пользователя ответа.

Цель — устранить несущественные Q и безопасные A, а оставшиеся группировать с сохранением технических границ.

## 2. Подтверждённые сведения и пробелы

Проверено по официальному коду `anomalyco/opencode` на **точном теге v1.19.0**:
- [tool/question.ts](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/opencode/src/tool/question.ts): один вызов `question` получает массив `questions` и возвращает соответствующий массив ответов.
- [question/index.ts](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/opencode/src/question/index.ts), [schema/v1/question.ts](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/schema/src/v1/question.ts): `question.asked`, `question.replied`, `question.rejected`, привязка к сеансу и инструменту.
- [question HTTP API](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/opencode/src/server/routes/instance/httpapi/groups/question.ts): получение ожидающих вопросов, ответ/отказ.
- [permission/index.ts](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/opencode/src/permission/index.ts): штатные правила, `pending`, `approved`, решение `always`; это отдельный контур.
- [permission HTTP API](https://github.com/anomalyco/opencode/blob/v1.19.0/packages/opencode/src/server/routes/instance/httpapi/groups/permission.ts): получение ожидающих разрешений и ответ на конкретный запрос.

**Особенность native reply:** в исследованном коде `Question.Service.reply` обращается к ожидающему запросу по `requestID`; одного наличия `sessionID` в событии недостаточно, чтобы считать вызвавшего API доверенным человеком. В тестовом контроллере до отправки синтетического ответа проверять идентичность экземпляра, сеанса, `requestID` и ожидаемого вызова. Для технических разрешений эти события тем более не являются удостоверением согласия пользователя.

**Границы этих сведений:** чтение исходников не доказывает работоспособность UI и HTTP API конкретного установленного `opencode.exe` или точную семантику событий на Windows. В `tests/compatibility/registry.json` отсутствует exact-профиль 1.19.0. В текущем main есть native permission runtime probe на Windows/1.18.32, но нет измеренного жизненного цикла пачки Q/A в 1.19.0. MP-3 пользовательский замер [agent-toolchain#61](https://github.com/dilukhin/agent-toolchain/issues/61) не закрыт.

Не предполагать, что `question` является каналом подтверждения опасных действий; не считать готовым штатный интерфейс пакетных A. Его наличие/отсутствие и API-ограничения исследовать отдельно, а не подменять широким `bash: allow`.

## 3. Автономный цикл и очередность решений

1. Агент принимает задачу и ограничения. Первым делом выполняет **допустимые** чтение, анализ и планирование, чтобы не задавать вопросы, ответы на которые уже есть в задаче или данных.
2. Определяет, какие действия дают штатный `ALLOW`, какие получают абсолютный `DENY`, какие требуют технического `ASK_USER`, а какие — содержательного решения Q. Анализировать **всю** операцию, включая составные и вложенные эффекты.
3. Независимые существенные Q, ответы на которые нужны для следующей фазы, объединяет в один вызов `question` с массивом вопросов. Не объединять предположения, ещё не подкреплённые фактами, и не раздувать пакет «впрок».
4. Пользователь отвечает одним заходом. Ответ изменяет рабочий план, **но не** `approved`, native rules, scope доверенного проекта или другое состояние полномочий.
5. Агент продолжает однозначные безопасные шаги без дополнительного «продолжать?». Запрещённое действие не пытается выполнить. При неожиданном состоянии останавливает затронутый путь, а независимые безопасные пути может продолжать.
6. Когда появились новые реальные решения Q или остаточные A, формируется следующий ограниченный пакет, а не серия бессодержательных одиночных остановок.

### Рекомендация для будущих managed instructions (не внедрена)

«Прежде чем спрашивать, собери доступные безопасные факты и проверь уже принятые решения. Независимые существенные вопросы объедини в один вызов `question`. Не спрашивай разрешения на очевидные действия, уже входящие в задание и допустимые техническими правилами. Не трактуй ответ на вопрос, текст плана или собственное предложение как техническое разрешение. После согласования выполняй последовательность до реального препятствия, не запрашивая подтверждение каждого промежуточного шага».

Инструкция направляет **планирование и общение**, но не служит средством принудительной защиты. Её распространение — ответственность `opencode_setup` / `agent-toolchain` после отдельной приёмки, без переписывания пользовательских инструкций.

## 4. Два этапа пакетирования: Q и A

### Q: использовать штатный механизм минимально

Первый практический вариант — **один вызов `question` с 2–5 независимыми вопросами** после доступной безопасной разведки. Число 2–5 — рекомендация для удобства, а не лимит интерфейса или формата OpenCode. Каждый вопрос:
- предлагает понятные альтернативы и, если есть, обоснованный предпочтительный вариант;
- не повторяет ответ, уже известный из текущей задачи;
- объясняет, какая часть работы от выбора зависит;
- допускает отказ или новый ввод, если это поддерживается исследуемым интерфейсом;
- не содержит секретов или ненужного технического вывода.

Если существенных вопросов нет, `question` не вызывается. Независимые разрешённые шаги по возможности завершать **до** блокирующего вызова `question`: нельзя считать, что остановившийся на вопросе сеанс OpenCode автоматически продолжит их параллельно.

**Первый доказательный тест Q1**: локальная имитация модели отдаёт один `question` с тремя вопросами; отдельный наблюдатель фиксирует один `question.asked`, проверяет `sessionID`/привязку к `callID`, выдаёт синтетический ответ в тестовом экземпляре и проверяет продолжение. Нужны также `reject`, расхождение ответов, потеря наблюдения и изоляция сеансов. В CI тестовые ответы не доказывают согласия человека.

### A: план согласования, но пока не runtime grant

Сначала построить **представление пакета**, в котором каждый элемент содержит:
- назначение и проверенные target/environment;
- точный распознанный intent и его эффекты; для подготовленной операции — связанные `executable/argv/cwd` и необходимые зависимости;
- исходное native + deterministic решение, отдельное обоснование остаточного `ASK_USER`, риск/обратимость;
- границу полномочия: конкретное действие либо подтверждённый узкий шаблон, срок/число использований, условия отмены и изменения контекста;
- отдельный выбор пользователя по элементу: подтвердить / отклонить / уточнить.

Это **логические требования к представлению**, а не предложение прямо сейчас вводить новый wire schema или новый сервис владельца согласий.

После фактического подтверждения доверенным механизмом:
- каждое A должно связываться с действием и заново проверяться перед его исполнением;
- подмена цели, эффекта, вложенной команды, контекста или разрешённого числа использований отменяет именно затронутое подтверждение;
- `DENY` нельзя повысить до `ALLOW` через пакет; unknown/opaque не становится автоматически разрешённым;
- частичный отказ не отменяет независимую безопасную работу и не подтверждает другие элементы;
- модель не может создать себе `approved`, вызвать правоответный интерфейс или выпустить grant только из текста Q/плана.

**Критично:** у штатного `always` могут оказаться более широкие шаблоны, чем одиночная команда. Нельзя автоматически превращать «согласен с пакетом» в серию `always`, пока точные шаблоны и область их действия не проверены отдельно. Использовать существующего владельца разрешений, а не создавать второго; если штатного механизма недостаточно, сначала предъявить конкретный gap и пройти отдельное архитектурное решение.

### A0: переиспользовать защищённого владельца, не строить второго

Уже существует испытательный владелец согласия: [#46 / PR #47](https://github.com/dilukhin/opencode_permissions/pull/47). Внешний процесс под отдельным Linux UID принимает решения через закрытый канал, связывает их с неизменяемой операцией и проверяет одноразовое потребление. Он проверен для синтетических операций; реальный ввод человеком, устойчивое потребление перед фактическим запуском и закрытие прямого обхода пока не доказаны. Native once, ответ Q и API authentication эти пробелы не закрывают.

[Контракт пакетирования существующего владельца](batch_approval_owner_contract_ru.md) задаёт неизменяемый перечень, один просмотр с отдельным решением по каждому элементу, индивидуальный одноразовый допуск и отрицательный корпус. Пакет не является транзакцией изменений. Частичный отказ блокирует зависимые действия; потеря ответа не разрешает повтор; stop/recovery не наследуют допуск start.

Первый кандидат ограничен **точными подготовленными операциями**, без будущих wildcard-полномочий. Сначала довести защищённое отдельное согласие до доказанной интеграционной границы, затем проверить его пакетирование. Защищённый профиль не навязывается безопасным автоматически разрешаемым действиям.

## 5. Измерение фактического снижения вмешательств

Раздельно собирать:
- `permission_request_count` — число native `permission.asked`;
- `question_request_count` — число native `question.asked`;
- `question_item_count` — суммарное количество вопросов внутри пакетов;
- `user_interruption_count` — число **действительных пользовательских прерываний** (отдельное наблюдение UI либо явно указанный измерительный суррогат);
- `batch_size` — количество существенных Q/A в одном обращении;
- `avoidable_question_count` — результат отдельной проверяемой классификации, а не эвристическое совпадение слов;
- `uninterrupted_execution_duration` — длительность активного выполнения, не подмена временем простоя;
- `unsafe_automatic_allow`, `hard_deny_bypass_count` — всегда ноль.

Ключевое правило: **отсутствие зафиксированного события не доказывает отсутствие запроса**, если поток наблюдения не подтверждён как полный. Статусы `PASS / FAIL / INCONCLUSIVE`; при потере корреляции, неизвестном сеансе или истечении ожидания — `INCONCLUSIVE`.

Привязывать записи к версии, платформе, конфигурации, `sessionID` и, когда доступно, `callID`. В публичные отчёты выносить обезличенные итоги, не команды, пути, секреты и необязательные пользовательские ответы. Счётчик запросов API не выдавать за число реально показанных окон.

## 6. Планируемые доказательные случаи

| ID | Сценарий | Ожидаемое наблюдение |
|---|---|---|
| Q01 | Три независимых существенных вопроса | Один `question.asked`, три элемента, верный `sessionID`; после test reply — продолжение |
| Q02 | Уже известное решение / несущественная неопределённость | Дополнительный Q не требуется; выполнение продолжается в пределах полномочий |
| Q03 | Отказ отвечать на пакет | Нет фиктивных ответов; затронутая работа останавливается |
| Q04 | Перепутан `callID`/потеря событий | `INCONCLUSIVE`, не ложный успех |
| Q05 | Контроллеру передан `requestID` от другого сеанса | Контроллер отвергает неверную корреляцию **до** отправки ответа; если штатный API допускает чужой ответ, это отдельно фиксируется как gap |
| A01 | Безопасная команда, native `ALLOW` | Не включать в пакет A |
| A02 | Hard `DENY` внутри пакета | Не выполняется и не допускается к повышению |
| A03 | Согласованы две операции, третья отклонена | Две ограничены своими identities; третья не выполняется |
| A04 | Изменились argv/target/effect/context после согласования | Старое согласие не действует |
| A05 | Повторное использование, expiry или revoke | Повтор отклоняется / возвращается штатный `ASK_USER` |
| A06 | `question` ответил «Да» или модель вставила `--approved` | Никакой новой технической авторизации |
| A07 | Составная/вложенная команда или wildcard с расширяющим смыслом | Нельзя получить общий shell `ALLOW` |
| M01 | Поток событий пропал перед вторым вызовом | `INCONCLUSIVE`, даже если stdout похож на ожидаемый |

Q1/Q2 — только синтетическая или изолированная среда до пользовательского пилота. A02/A04/A07 — parser-only/mock/temporary fixtures, без реальных разрушительных действий.

## 7. Gates и владельцы

**Q0 — текущий этап:** source review, компактное техническое решение, программа тестов, отдельный проектный PR. Документ сам по себе ничего не развёртывает.

**Q1 — после review Q0:** расширить уже имеющийся `tests/compatibility` и mock provider для двух независимых вызовов и `question`; подтвердить exact OpenCode 1.19.0 без внешней GPT и без пользовательского подтверждения. Не переводить 1.19.0 в deployable без полной exact compatibility revalidation.

**Q2 — после Q1:** ограниченный измерительный пилот группирования рабочих вопросов, сравнение количества фактических остановок и качества решений; распространять managed instructions через владельца установки.

**A0 — допустимое параллельное проектирование:** [контракт пакетирования](batch_approval_owner_contract_ru.md) на основе существующего защищённого владельца PR #47 и AuthorizationGrant; отрицательный корпус, точная привязка, доверенная подготовка и устойчивый барьер agent-safe. **Никаких новых технических ALLOW**. Приёмка отдельного защищённого согласия предшествует пакетному допуску.

**A1 — заблокировано до MP-3 baseline и конкретной совместимости:** выбирать одну measured residual-ASK family, реализовывать минимальный механизм только если недостаточно штатного узкого `permission`. Нужна отдельная приёмка и демонстрация `unsafe_automatic_allow = 0`.

**A2 — после A1:** системные/отрицательные проверки в CI, локальное явное подключение через `opencode_setup` / `agent-toolchain`, наблюдение/откат. Не изменять live permission config автоматически.

Границы: `opencode_permissions` — решение о разрешении и точная привязка; `agent-safe` — рискованные state-changing операции, verify/recovery; `opencode_setup` — установка/управляемые инструкции; `ssh_relay` — удалённый транспорт и контракт результата. Преждевременный новый broker, отдельный аудитор или общий пакетный API запрещены без доказанной необходимости.
