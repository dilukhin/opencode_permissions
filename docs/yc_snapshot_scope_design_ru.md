# YC: адресная проверка снимка и граница разрешения изменений

Статус: **A0 — проект решения и исполняемая фиксация текущей границы**.
Связанные задачи: [#59](https://github.com/dilukhin/opencode_permissions/issues/59),
[#55](https://github.com/dilukhin/opencode_permissions/issues/55).
Этот этап не выпускает новую policy, не включает getters и не закрывает #59.

## 1. Подтверждённое ограничение и решение A0

`tools/classifier_yc.py` проверяет exact argv по канонической policy.
`<resource_id>` проверяет форму ID; это не доказательство принадлежности ресурса
выбранной ВМ. В `parsed-simple/v1` для YC нет доверенно полученной области
VM/disk/snapshot. Поля `trusted`, `approved`, произвольные `targets` и заявление
вызывающей стороны о владельце такую область не создают.

`runtime/yc_guard/yc_transitional_adapter.py` разрешает передачу executor только
для `ALLOW`; `ASK_USER` и `DENY` не исполняются. Adapter не имеет интерфейса
доверенного одноразового подтверждения. Наличие `operation_identity` у ASK
связывает описание операции, но не создаёт право её выполнить.

Управляемый потребитель `agent-toolchain/yc_transitional_entry.py`, функция
`_dispatch_guard`, запускает разрешённый downstream через `subprocess.run`
с наследуемыми stdout/stderr. Проекции ответа в этом пути нет. Заблокированный
ASK возвращает rc 78 и не ожидает интерактивного ответа.

**Решение этого этапа:** новые `disk get` / `snapshot get` остаются `ASK_USER`.
Публиковать общий `<resource_id>` для этих getters сейчас нельзя: нет привязки
к выбранной цели и нет границы выдаваемых полей. Ручное свидетельство владельца
из консоли принимается только как `owner_console`, отдельно от независимого
наблюдения guard. Оно не меняет policy и не открывает executor.

Этот вывод не отменяет существующие ALLOW для instance/SG/subnet и не расширяет
их на новые ресурсы. Проверка ранее принятого выпуска G3/G4 не повторяется.

## 2. Проверенный синтаксис и минимальное чтение

По официальному справочнику оба getter поддерживают `--id`; `--format json`
является отдельным глобальным флагом. Это подтверждение документации,
а не проверка установленной версии CLI или фактических IAM-прав.

| Кандидат точного argv | Условие будущего допуска | Сейчас |
|---|---|---|
| `yc compute disk get --id D --format json` | D заранее связан с выбранной ВМ доверенным наблюдением | ASK_USER |
| `yc compute snapshot get --id S --format json` | владелец отдельно разрешил чтение exact S для проверки выбранного D | ASK_USER |

Только эти два getter входят в следующий минимальный срез. Имена, позиционные
ID, aliases, `--id=`, дополнительные/повторные флаги, list снимков, Cloud Backup
и новые сетевые getters в него не входят. Caller-controlled `--jq` не заменяет
проверенную проекцию. Допуск обычного `get --id` с полным выводом не подразумевается.

Документация:

- [CLI Disk.Get](https://yandex.cloud/en/docs/compute/cli-ref/disk/get).
- [CLI Snapshot.Get](https://yandex.cloud/en/docs/cli/cli-ref/compute/cli-ref/snapshot/get).
- [API Disk.Get](https://yandex.cloud/en/docs/compute/api-ref/Disk/get).
- [API Snapshot.Get](https://yandex.cloud/en/docs/compute/api-ref/Snapshot/get).

Для будущей фиксированной проекции достаточно следующих полей:

| Ресурс | Разрешённые поля результата | Что сверять |
|---|---|---|
| disk | `id`, `folder_id`, `status`, `size`, `type_id`, `zone_id`, `instance_ids` | exact D, ожидаемый каталог, связь с выбранной ВМ |
| snapshot | `id`, `folder_id`, `status`, `source_disk_id`, `disk_size`, `created_at` | exact S, ожидаемый каталог, исходный D и готовность |

Здесь snake_case — целевое внутреннее представление; REST использует camelCase.
Отображение полей конкретного YC CLI нужно отдельно подтвердить перед реализацией.
Размеры сохранять десятичными строками без потери int64. Не выдавать имена,
описания, labels, metadata/user-data, product IDs, сведения KMS, raw stdout/stderr
и неизвестные дополнительные поля. Ошибки выдавать как ограниченный проверенный
код; отладочный вывод не отправлять модели и не сохранять в журнал.

`snapshot.source_disk_id` связывает снимок с диском; `disk.instance_ids`
описывает текущие подключения диска. Эти сведения вместе с ранее наблюдённой
конфигурацией дисков ВМ нужны для проверки цели. `source_snapshot_id` у диска
имеет другое направление: это источник создания диска, а не снимок этого диска.
Состояние `READY` и совпадение ID не доказывают согласованность данных приложения
или возможность восстановления ВМ. Эти проверки принадлежат `agent-safe` и
плану восстановления. Изменение размера/подключений диска после снимка требует
новой проверки контекста, а не автоматического вывода об ошибке или готовности.

## 3. Как должен появиться доверенный scope

Следующий этап должен переиспользовать владельца разрешений, а не создавать
вторую таблицу доступа в setup. Модель передаёт запрос, но не получает возможность
выдавать или изменять разрешение. Конкретный транспорт для Windows ещё не выбран
и не реализован; этот документ не объявляет in-process прототипы рабочим IPC.

Будущее разрешение чтения связывает exact argv, владельца/сессию запроса,
cloud/folder/VM/D/S, версию проекции, срок и свежесть наблюдения исходной цели.
Реальные IDs остаются в защищённом состоянии владельца, не в публичной policy.
При смене цели, истечении срока, несовпадении ответа или потере состояния —
отказ без расширения доступа, слепого повтора и перехода к прямому `yc.exe`.

Важно различать два допуска:

1. **До запроса:** доверенный владелец разрешает прочитать именно S. Переданный
   человеком ID сам по себе не является машинным доказательством этого разрешения.
2. **После ответа:** проверяется, что S действительно относится к D и ожидаемому
   каталогу, затем наружу выходит только фиксированная проекция.

Проверка `source_disk_id` после загрузки не может задним числом разрешить уже
совершённое чтение чужого объекта. Если исходное разрешение на exact S отсутствует,
YC не вызывается. При несоответствии после разрешённого чтения сырой ответ не
выдаётся. Поведение при сбое/таймауте и повторе должно быть явно согласовано с
одноразовостью; не обещать ровно один HTTP-запрос по одному запуску CLI.

## 4. Временный путь: свидетельство владельца

Для вручную созданного снимка владелец может отдельно сообщить из YC console
минимум: выбранную ВМ, исходный диск, ID снимка, его исходный диск, каталог,
статус, размер диска на момент снимка и время создания. Приватные значения не
публикуются в GitHub. Не просить raw config, IAM keys, metadata или полный JSON.

При сопоставлении сохранять `evidence_source=owner_console` и время наблюдения;
явно указывать `independent_guard_readback=false` и
`restore_verified=false`. Это смысловые отметки свидетельства, не новый wire
protocol и не токен допуска. При недостатке/противоречии полей результат остаётся
неподтверждённым. Создание, удаление, остановка ВМ и восстановление из этого
документа не следуют и автоматически не выполняются.

## 5. Изменения облака: отдельный проект авторизации

Существующее переходное исключение — только две exact операции start/stop одной
закреплённой ВМ. Для новой ВМ действует #55. В A0 `allow_mutations` не меняется.

Будущий адресный путь должен связать согласие с exact argv/целями, свежим
состоянием, владельцем, сроком, стоимостью и квитанцией исполнения. `--approved`,
`approved=True`, UUID и JSON от агента не являются согласием владельца.

| Операция | Необходимая отдельная граница |
|---|---|
| start/stop новой ВМ | #55: exact VM, исходный статус, последствия стоимости/доступности |
| snapshot create | exact исходный D; согласованность данных; стоимость; серверный ID из проверенного результата |
| snapshot delete | собственный exact S; проверенное происхождение; удаление не считать универсальным rollback |
| disk create/restore | exact исходный S; новая идентичность результата; отдельный план подключения/возврата |
| SG/network update | exact объект и ожидаемые правила; сохранение доступа; проверяемый план восстановления |

`opencode_permissions` принимает и связывает решение. `agent-safe` отвечает за
checkpoint, журнал, однократное потребление перед внешним эффектом, проверку
результата, unknown/recovery. Транспорт и установка остаются у своих владельцев.
После неизвестного результата запрещён автоматический повтор mutation; сначала
проверка фактического состояния. Потеря квитанции не возрождает согласие.
Динамический ID создаваемого объекта связывается после проверенного результата;
нельзя заранее утверждать, что команда удаления ещё неизвестного S — исполнимый
rollback. В этом этапе отсутствуют новый approval transport и cloud executor.

## 6. Исполняемая проверка A0 и следующие условия

`tests/yc_snapshot_boundary_cases.json` фиксирует текущую границу. Тест
`tests/test_yc_snapshot_boundary.py` проверяет решения и отсутствие вызова
имитации executor при ASK/DENY, поддельные claims/console evidence, запрет
caller-controlled approval и сохранение двух прежних lifecycle-операций.
Отдельный Python-процесс загружает материализованный content-bound артефакт,
чтобы не принять уже импортированный исходный модуль за упакованный runtime.
Все IDs синтетические; реальные YC и опасные команды не исполняются.

A0 закончен после проверки документов, тестов исходников и упакованного runtime
и CI на точном PR HEAD. Это не критерии закрытия issue целиком.

Следующий **A1** — реализация доверенного адресного чтения и проекции. До ALLOW
нужны выбранный поддержанный источник разрешения, точная привязка контекста,
ограничения размера/времени ответа и тесты отсутствия утечки/dispatch при отказе.
Нельзя закрыть это условие добавлением wildcard в JSON. Тесты A0 при таком
осознанном изменении обновляются вместе с новым контрактом и негативным корпусом.

Компонент проверки полей ответов реализован отдельно:
[`yc_read_projection_ru.md`](yc_read_projection_ru.md). Он не выдаёт разрешений
и пока не подключён к dispatcher. Это готовая часть A1, а не закрытие всего A1:
доверенный источник адресного допуска, ограниченный захват ответа и сквозная
интеграция остаются обязательными до нового ALLOW и выпуска.

Затем **A2** — новый content-bound artifact, reviewed pin в `agent-toolchain`,
штатный old-active → new-active upgrade с checkpoint/journal/OS lock,
независимый read-back installed shim и сохранённый старый fallback. Не править
installed policy/shim вручную. Только после этого допускается приёмка нового
чтения. Никаких cloud mutations при проверке policy.

**B** — отдельная реализация адресной авторизации mutations совместно с #55
и `agent-safe`. A1/A2 не закрывают B, а состояние READY не закрывает восстановление.
В A0 payload policy/runtime не меняется, поэтому новый artifact/pin и обновление
машины для этого PR не требуются. Закрывать #59 и #55 этим PR нельзя.
