# YC59: проверка владельца согласия на Windows

Статус: изолированный испытательный транспорт; установка не разрешена.

После наблюдения native once на OpenCode 1.19.5 остаётся более сильное
требование: процесс агента не должен сам выдавать согласие от имени человека.
Обычный ответ HTTP API OpenCode такого происхождения не доказывает.

## Что проверяет этот опыт

На временной Windows-машине GitHub Actions создаётся отдельная локальная
учётная запись без административных полномочий. Реальный дочерний процесс
запускается через `CreateProcessWithLogonW` с её токеном, без наследования
секретов окружения CI. Пароль случайный, остаётся в памяти владельца,
не передаётся в командной строке или журнале. После опыта созданная учётная
запись и её временный каталог удаляются. На установленном компьютере сценарий
отказывается работать до создания учётных записей и каналов.

Используется **неизменённый Ledger существующего владельца** из PR #47,
закреплённый полным commit SHA и SHA-256 файла в `tests/yc59_windows/pins.json`.
Он загружается только как испытательная зависимость; Linux-сервер не запускается.
Новый реестр разрешений или параллельный владелец не создаются.

Два именованных канала Windows имеют явные защищённые DACL:

| Канал | Доступ | Источник личности |
|---|---|---|
| agent | SYSTEM, владелец, выбранная учётная запись агента | SID `TokenUser` после чтения сообщения и `ImpersonateNamedPipeClient` |
| decision | SYSTEM и владелец; агенту ОС отказывает в открытии | тот же SID из токена ОС |

Удалённые клиенты запрещены. Создание канала требует первого экземпляра;
агенту не выдано право `FILE_CREATE_PIPE_INSTANCE`. Клиент сверяет PID сервера
через Windows API с PID из доверенной настройки испытания. SID из JSON никогда
не используется как удостоверение личности. При ошибке impersonation запрос
не передаётся реестру; невозможность `RevertToSelf` завершает процесс.

Испытание проверяет pending до решения, отказ агенту в самоподтверждении и
доступе к decision, отказ подставленному полю uid и неверному PID сервера,
просмотр сохранённой операции владельцем, точный digest, однократное
потребление, отказ повтору и отклонённому запросу. Свежий экземпляр того же
Ledger не восстанавливает старое разрешение. Это проверка новой эпохи реестра,
не испытание восстановления после аварии процесса.

## Границы вывода

Решение принимает **автоматический испытательный клиент под учётной записью
владельца**. Это доказывает разделение процессов по учётным записям ОС,
но не присутствие человека. Используется исходная синтетическая операция
`sudo_job.start` существующего прототипа. Никакие команды операции, SSH, sudo
или YC не исполняются. Она не объявляется чтением YC и не выдаёт разрешение
для снимка. OpenCode в этом опыте не запускается.

Транспорт намеренно остаётся испытательным: блокирующий клиент может занять
канал; остановку ограничивает внешний срок CI. Нет защищённого установщика,
службы, интерфейса человека, постоянного журнала, восстановления согласия,
полного испытания отказа в доступе к процессу владельца или защиты от
администратора/SYSTEM. Совпадение SID агента и владельца запрещено. Изменение
ACL, импорта или токена в скомпрометированном доверенном процессе не покрыто.

Для завершения #59 ещё нужны защищённый путь решения человека, согласование
контракта YC с существующим владельцем, привязка разрешения к точным
folder/VM/disk/snapshot, процессу и версии политики, ограниченный захват
ответа и безопасная проекция, затем управляемая поставка и проверка на
установленной Windows-системе. Текущий опыт не разрешает обновление guard,
изменение policy/artifact, прямой REST или запуск скрытого `yc.exe`.
