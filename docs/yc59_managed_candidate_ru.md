# YC59: кандидат управляемого выпуска

Сборщик по умолчанию продолжает выдавать неактивную библиотеку v1. Явный
`--candidate-source-ref` формирует отдельный кандидат v2 из тех же точных байтов.
Он имеет другой домен идентичности и не принимается проверкой неактивной
библиотеки. Источником манифеста и полномочий остаётся opencode_permissions;
toolchain копирует опубликованные байты и не меняет правила или флаги.

Опубликованный кандидат использует проверенный ref
`9ece957d76b0a5a41caa05956c1665543614ef82`, 16 файлов компонента #71. Manifest
содержит их размеры/SHA-256, точный ref и карту исходников. Сопоставление байтов
по этим данным обязательно до загрузки Python. Проверка хеша изменяемым агентом
Python не заменяет внешнего нативного корня.

`execution_enabled=true` означает допустимость запуска этого кода **только**
через `yc-owner-native/v1` при выполненных условиях манифеста: закреплённый
нативный bootstrap, отдельные обычные учётные записи, защищённый полный выпуск,
управляемая блокировка и журнал. Он не означает выданного согласия. После
запуска каждый запрос всё равно требует точного решения владельца в его
локальной консоли и расходуется единственным Ledger до первого процесса YC.

Native bootstrap обязан подготовить новый закрытый каталог, проверить точный
Python/YC/компонент, удерживать объекты и предков, защитить process/token/default
DACL до первой инструкции Python, ограничить всю группу потомков и не допустить
двух активных владельцев через общую защищённую блокировку владельца. При
частичном журнале — отказ без ремонта. Предыдущий выпуск сохраняется. Старые
согласия после завершения процесса не восстанавливаются и не мигрируют.

Кандидат не утверждает installed acceptance: `installed_acceptance=false`.
После завершения управляемой поставки нужна короткая фактическая приёмка на
Windows с реальными выбранными ID и личным разовым решением владельца.
Ни создание этого манифеста, ни CI, ни HTTP/API `once` таким решением не являются.
