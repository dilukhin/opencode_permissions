# YC59: ограниченный Windows-транспорт и модуль владельца

Этот компонент заменяет блокирующий транспорт испытательного прототипа.
Он ещё не является разрешением на установку или готовым облачным исполнителем.

## Что реализовано

`tools/windows_owner_pipe.py` использует асинхронные операции Windows
(`OVERLAPPED`), события и `CancelIoEx`. На подключение, чтение и передачу ответа
отводится ограниченный срок. После ответа клиент посылает однобайтовое
подтверждение; `FlushFileBuffers` отсутствует. Зависший клиент отключается,
затем тот же экземпляр принимает следующий запрос. Одновременно существуют
только два рабочих потока, по одному на канал агента и канал решения владельца.
Сообщение ограничено 64 КиБ. Сырые запросы и причины системных исключений
не сохраняются в диагностике транспорта.

Канал допускает только локальные подключения. Защищённый DACL не даёт агенту
создавать экземпляры pipe; `FILE_FLAG_FIRST_PIPE_INSTANCE` отклоняет занятое имя.
SID и SessionId клиента получаются из токена после чтения его сообщения.
Клиент до передачи запроса получает PID сервера у ядра, открывает процесс и
проверяет TokenUser/TokenSessionId. Совпавший PID при другом SID/сеансе не
принимается. Ожидаемый субъект должен поступать из защищённого запуска;
произвольный JSON с SID не становится источником доверия.

Для клиента другого SID сервер добавляет **только**
`PROCESS_QUERY_LIMITED_INFORMATION` на собственный процесс и `TOKEN_QUERY` на
собственный токен. Старые ACE сохраняются для остальных субъектов. Для точного
SID агента отдельно запрещены остальные права: старые групповые ACE иначе могли
бы оставить доступ TOKEN_DUPLICATE. Duplicate/impersonate/adjust, запись памяти
и управление процессом закрыты, SeDebugPrivilege не включается.
Это узкие права чтения двух текущих объектов ядра на срок их жизни, а не изменение
пользователей, групп или файловых ACL. Межсубъектный CI проверяет настоящий
непривилегированный клиент и отдельно отсутствие TOKEN_DUPLICATE/PROCESS_VM_WRITE.
Он переиспользует уже существующую временную CI-учётную запись испытания.

Каждое сообщение агента также проверяется по настоящему токену: обычный
неповышенный субъект, низкий/средний уровень целостности, отсутствие
административных/операторских групп (включая deny-only Administrators),
повышаемого linked token и привилегий вне узкого списка обычного пользователя.
Неизвестные свойства/привилегии вызывают отказ. Проверка не меняет токен или
группы; отчёт SID не удовлетворяет этому условию. Она не заменяет защиту процесса
и его файлов **до** запуска Python: это всё ещё отдельное условие активации.

Источники семантики Windows:
[OpenProcessToken](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocesstoken)
и [SetEntriesInAclW](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setentriesinaclw).

При остановке отменяются незавершённые операции, выполняется ограниченное
ожидание потоков и освобождаются дескрипторы. Если ОС не подтверждает завершение
отменённой операции за секунду, процесс завершается с кодом 70: нельзя освободить
буфер, на который ещё ссылается ядро. Функция обработки запроса принадлежит
доверенному запуску и должна сама соблюдать срок до 35 секунд. Транспорт
не превращает произвольную зависшую функцию Python в ограниченный исполнитель.

`runtime/approval_owner/ledger.py` — перенос того же автомата из закреплённого
`tests/opencode_2_0_23/approval_owner.py` на commit
`6ddac8d8a29c5c660fd373d9b2caa08735ed7a51`, SHA-256
`d81f306b2a41b71f274c7e18841f6be8dd1785c1005f6e5860b823bdbd541bab`.
Перенесены `Refusal`, `strict_json`, `keys`, `Ledger`; Linux-сокеты, консоль,
CLI и sudo-job canonicalizer не входят. Для конструктора canonicalizer теперь
обязателен. Переходы и однократное потребление не изменены. Черновой PR #47
не сливается, испытательный pin не поднимается и второй Ledger не создаётся.

`runtime/approval_owner/read_host.py` соединяет этот единственный Ledger,
точный профиль чтения и новый транспорт. Строгое разделение ненулевых
Windows-сеансов отключить нельзя. Запрос дополнительно привязан к сеансу
агента, который его создал: другой сеанс того же SID не может его потребить
или отменить. Происхождение для консоли возвращается из наблюдения ядра.
Остановка отменяет неиспользованные разрешения и закрывает последующие запуски.

## Проверяемая граница

Переносимый корпус проверяет автомат, точные argv, drift, DENY, replay,
конкурентное потребление, потерю результата, отказ запуска и безопасную проекцию.
Отдельные тесты Windows используют настоящие локальные pipe и токены процесса,
включая зависших клиентов, отсутствие подтверждения ответа, подмену субъекта
сервера, занятое имя и остановку. Они не создают учётные записи и не вызывают YC.
Положительный транспортный тест в одном CI-сеансе не считается человеческим
согласием. Строгий host проверяется отдельно с синтетическими субъектами.

## Что ещё требуется для рабочего пути

У host пока нет публичного запуска. Его конструктор принимает только функции
доверенного кода: текущий ReadContext, текущий native veto и точный запуск.
Это интерфейсы подключения, а не доказательство их происхождения. Подставить
постоянный `ask`, сведения из JSON агента или скрытый downstream нельзя.

Следующий компонент обязан защитить запуск **до** исполнения Python:
интерпретатор, DLL/stdlib, payload, конфигурацию, состояние и их родительские
каталоги; проверить фактические права агента, включая административные группы;
обеспечить доверенные источники контекста/запретов и повторную проверку при spawn.
После этого возможны точный артефакт, reviewed pin, управляемая активация и
установленная приёмка настоящего YC. Проверки файлов внутри изменяемого агентом
Python не заменяют эту границу.

Наблюдения агента и владельца уже сопоставлены. Повторять пробники или создавать
ещё одну учётную запись для этой реализации не требуется. Старый guard,
каноническая policy и её ALLOW остаются прежними; #59 и #120 пока открыты.
