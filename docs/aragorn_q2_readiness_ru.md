- Средства Docker/Podman/virsh не найдены; доступ к /dev/kvm не означает готовую VM/изоляцию.
- Раздельные UID, терминал владельца и изоляция credentials не подтверждены. Защищённое исполнение не запускается.
- Exact P0 profile 2.0.23 отсутствует. Версия не понижается; registry не расширяется ради удобства опыта.

Повторная полная инвентаризация не нужна. Отсутствие P0 profile не является запретом готовить независимый опыт Q, но успех Q не открывает P0/A1.

## Изменения протокола в 2.0.23

Проверен точный upstream tag v2.0.23, commit 0fd7e2829449b052abf0078666669302923d77af. QuestionTool использует Form.Service; формы имеют поля q0/q1/q2, metadata.kind=question и tool.messageID/id. Перед созданием формы вызывается реальный Permission.assert(action=question). Поэтому следует раздельно учитывать технический ASK самого question и форму с вопросами.

Form.reply принимает карту значений, а не V1 answers array. Неизвестные поля отклоняются. Поля question не объявлены required: частичный ответ штатно допустим и преобразуется в пустые ответы для пропущенных вопросов. Контроллер не должен считать это полным согласованием требований или придумывать ответы. Form.ask при прерывании вызывает cancel; это не доказательство того же поведения полной цепочки session.abort/UI.

## Автоматическая проверка перед рабочим пилотом

tests/opencode_2_0_23/question_form_boundary.test.ts исполняется внутри закреплённого upstream с Bun 1.4.2 и frozen lockfile. Реальны QuestionTool, Tool registry, Form, Permission и Bus; заменены только Location временного испытания и image passthrough, изображения не используются. Локальная БД/сеансы синтетические; внешняя модель и исполнение команд отсутствуют.

Корпус: один пакет/три последовательные формы, точный порядок ответов, DENY и ASK самого question, неверное поле/частичный ответ, cancel/interruption/close, фильтрация по сеансам, отсутствие переноса Q в другую permission-операцию. Фильтр sessionID — свойство наблюдения, не источник доказательства личности человека.

Успех этого workflow подтверждает уровень настоящих сервисов точного upstream. Он не подтверждает installed binary происхождение на aragorn, полный Session runner, HTTP/UI, отсутствующие сторонние слои или actual_human_ui_proof. Это не deployable compatibility profile и не реализация защищённого владельца из PR #47.

## Следующий локальный опыт

После проверки сервисов подготовить один ограниченный опыт настоящего установленного question/UI, с фиксированной моделью openai/gpt-6-sol, без установки/обновления и без включения P0. Фактическую выбранную модель подтвердить в интерфейсе перед замером; если недоступна, остановить этот опыт, не подставлять другую автоматически.

Сначала подтвердить полный путь создания/ответа/отказа/отмены на одном синтетическом вопросе; пользователь отвечает сам. Затем одинаковые задачи до/после группирования, с прямым счётом пользовательских остановок и отдельным счётом permission ASK самого question. Инструкции меняются только внутри испытуемого задания; управляемая установка идёт через своего владельца после приёмки, не путём правки global config.

До установленного UI proof Q2 остаётся незакрытым. Служебный тест в CI не заменяет локальное наблюдение, а Linux-отчёт не является измерением «до/после».
