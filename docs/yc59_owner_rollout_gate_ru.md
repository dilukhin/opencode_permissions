# YC59: условие поставки владельца Windows

Проверено 02.11.2026. Рабочая A1/A2 заблокирована; #59 не закрывать.

Исполняемая связка #65 остаётся испытательной. В текущем agent-toolchain нет
управляемого владельца согласия и доверенных поставщиков ReadContext/native veto.
Нельзя включить эту связку только новым pin или `toolchainctl update --apply`.
Нельзя превращать успешный CI в разрешение на самостоятельный вызов downstream.

## Принятое направление

OpenCode остаётся под прежней учётной записью агента. Владелец запускается под
другой защищённой учётной записью, в **другом интерактивном сеансе Windows**.
Для выбранного варианта пользователь входит в неё штатным экраном входа Windows.
Создание учётной записи, выбор её полномочий и вход не выполняются скриптом
проверки и не поручаются агенту как «попутная настройка».

Это консервативный контракт размещения. Доказательство разных SID в одном
сеансе подтверждает ACL канала, но не доказывает защиту пользовательского ввода
владельца. Присутствие терминала, `runas` или новый SID не заменяют проверки
Windows SessionId. Не заявляется, что в CI воспроизведена подделка ввода консоли;
до отдельного доказательства общей среды ввода её не принимать как доверенную.
Администратор/SYSTEM и компрометация доверенного процесса остаются вне заявленной
защиты; схема не является универсальной защитой от вредоносного ПО.

`tools/windows_owner_boundary.py` проверяет:

- точный выбранный SID агента и отличающийся SID владельца;
- ненулевые Windows SessionId обоих процессов;
- отличающиеся Windows SessionId.

На живом пути источником являются токены ОС: `TokenUser` и `TokenSessionId`
у владельца и у клиента после чтения сообщения/impersonation. JSON, отчёт,
параметр командной строки с чужим SID или dataclass не удостоверяют субъект.
Проверка выполняется до создания pending-запроса и до выдачи результата.

Испытательный Server теперь требует эту границу по умолчанию. Положительные
синтетические опыты одного сеанса явно выбирают
`require_separate_sessions=False`; это настройка только доверенного тестового
кода, не поле протокола. Отчёт помечает их как
`same_windows_session_transport_fixture_only` и
`separate_interactive_sessions_proven=false`. Отдельная проверка настоящих
токенов CI доказывает отказ строгого режима без создания pending-записи.

## Недостающее внешнее свидетельство

Нужны две минимальные записи с DIMA-HP: фактические SID/SessionId процесса
агента и предполагаемого владельца, запущенного через штатный вход Windows.
Предыдущий YC59-PREFLIGHT-01 этих сведений не собирал. Web не имеет доступа
к этому компьютеру или его экрану входа; CI создаёт другие субъекты на другой
машине. Подставить их значения в установку нельзя.

`tools/yc_owner_actor_probe.py` собирает только токен текущего процесса,
признаки терминала, путь/версию/хеш своего Python. Запись — только в новый
явно выбранный отчёт; команда запуска использует `python -B`. Нет subprocess,
сетевых обращений, YC, чтения config/credentials, создания пользователей,
служб/задач, обновления, записи памяти агента или исправления ACL.
Сравнение двух отчётов остаётся свидетельством исполнителя, не авторизацией.
Даже положительный результат всегда сохраняет `deployment_ready=false`.

Если отдельной учётной записи/сеанса нет, достаточный ответ — сообщить это.
Не создавать их автоматически ради получения положительного отчёта.
Если конфликтующая инструкция требует записи памяти/изменений вне каталога
задания, остановиться до выполнения, а не повторять отклонение PREFLIGHT-01.

## Что ещё обязан завершить Web после выбора реального размещения

1. Закончить единственный поставляемый владелец: ограниченные сроки IPC и
   завершение, проверка серверного субъекта, защищённый источник native veto,
   повторное получение ReadContext и проверка исполняемого файла/config на spawn.
2. Собрать content-bound компонент с проверенными исходниками владельца;
   текущая закреплённая зависимость черновика #47 сама не является такой поставкой.
3. Подключить owned staging/check/apply у agent-toolchain без смены старого
   active guard, ручной правки shim/policy, автоматического принятия чужого
   каталога или передачи второго владельца разрешений установщику.
4. Проверить точный артефакт/коммит в CI, затем подготовить единую ограниченную
   локальную приёмку: человеческое решение на точную цель, штатный upgrade,
   независимый installed read-back, безопасная выдача, отказ drift/replay.
5. Только после фактической приёмки включать рабочий допуск и закрывать A1/A2.

Это оставшаяся разработка Web, а не задача локальному агенту «дописать runtime».
До неё не выдавать команду установки существующего прототипа. Реальные ID
cloud/folder/VM/disk/snapshot понадобятся лишь для частной адресной приёмки;
в GitHub их не публиковать. Мутации облака и #55 остаются отдельной работой.
