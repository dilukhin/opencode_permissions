# Одиночный защищённый допуск: граница следующей интеграции

Статус: проектный контракт и программа проверки; исполнительный механизм не реализован. Продолжение пункта 4 принятого плана. Приёмка одиночного допуска предшествует пакетированию.

## Доверенная подготовка до показа

Агент может предложить намерение. Защищённая сторона сама определяет executable/argv/cwd, проверяет код и разрешённые зависимости, получает SSH identity из транспорта, фиксирует policy revision, execution host, UUID операции и задания. Файл identity, строка relay и JSON агента не являются доверенным доказательством.

Текущий canonical из PR #47 связывает command/hash, argv/executable/cwd и SSH identity. Для реального agent-safe start этого недостаточно: необходимо связать также expected state, точную read-only verify-команду и её hash, recovery plan/hash, timeout и флаги, меняющие границы риска (включая allow_critical). Значения, влияющие на исполнение, нельзя добавлять после согласия. Формат расширять в существующем контракте операции после сопоставления с PreparedProcess/NormalizedOperation; второго канонизатора и универсальной оболочки не вводить.

Проверяемый результат подготовки — одна сохранённая запись. Защищённая консоль показывает именно её. Перед запуском проверяется соответствие действительного вызова этой записи. Реконструкция и повторный разбор агентского shell-текста после согласия недопустимы. В частности, нынешний `_build` требует разделения подготовки и запуска либо проверки точного подготовленного результата до `_run`; простая подстановка approved=True этого не решает.

## Минимальная последовательность устойчивого исполнения

Не требуется обещать атомарность двух независимых журналов. Для первого варианта допустима потеря неиспользованного допуска при аварии, но повторное исполнение запрещено.

1. Защищённый владелец хранит решение и точную операцию. Агент не пишет решения/потребления/журнал и не получает исполняемый bearer-token.
2. Защищённый исполнитель перепроверяет DENY, контекст, срок, целевую identity и prepared operation. Только этот исполнитель может потребить допуск; публичный synthetic consume не подключается к запуску.
3. Владелец устойчиво отмечает однократное потребление **до** выдачи разрешения на отправку. Ошибка записи, повтор или неизвестный результат закрывают путь; перезапуск не переиздаёт допуска.
4. agent-safe создаёт устойчивый pending барьер и запись допуска/точной операции перед отправкой. Журнал размещён за защищённой границей. Обе записи сверяются; несовпадение или отсутствие любой блокирует dispatch.
5. Защищённый исполнитель отправляет один точный вызов транспорта. Между последней проверкой и dispatch нужна сериализация, исключающая подмену и некорректную гонку cancel/start. После начала dispatch отмена не становится stop; stop согласуется отдельно.
6. agent-safe учитывает результат, проверку и восстановление. Потеря ответа/авария сохраняет неизвестный результат и блокирует повторную мутацию. Разрешена только доказанно безопасная диагностика той же цели/задания.

Потребление без отправки может требовать нового явного решения после диагностики; это приемлемая цена первого fail-closed варианта. Запуск без записанного потребления неприемлем. fsync файла не равен полной гарантии против отказа накопителя: реализация обязана задать класс аварий, восстановление повреждённой записи, блокировку конкурентов и проверяемую сохранность каталога/барьера.

## Матрица приёмки одиночного допуска

Сначала mocks и одноразовые временные каталоги; реальная SSH/root операция — только в изолированной системе после предыдущих условий.

| Проверка | Обязательный результат |
|---|---|
| Изменение argv, executable, cwd, verify, expected state или critical-флага | Нет dispatch; требуется новое решение |
| Подмена identity-файла, host key, поколения или protected code | Нет dispatch |
| Native once/always, Q=Да, approved=True/--approved от агента | Не создают защищённого допуска |
| Агент вызывает прежний relay/API или читает credentials | Нет пригодного прямого канала; иначе приёмка FAIL |
| Отказ записи consumption или journal/barrier | Нет dispatch, нет автоматического повтора |
| Авария после consumption, до journal или до dispatch | Потерянный допуск не восстанавливается; состояние исследуется read-only |
| Авария после dispatch, ответ потерян | Unknown; start не повторяется; диагноз по тому же job/target |
| Конкурирующие потребления/запуски | Не более одного dispatch |
| Cancel состязается с dispatch | Заданная точка отмены; после отправки нужен отдельный stop |
| Start разрешён, stop/recovery предложены | Новые роли/допуски, без наследования start |
| Агент изменяет journal или protected operation | Технический отказ; отсутствие защищённого размещения блокирует запуск |

Каждый fault point должен иметь доказательство числа dispatch, состояния сохранённого допуска и барьера, а не только возвращённого кода. Преднамеренно сломанный проверяемый инвариант обязан дать FAIL.

## Порядок и локальная часть

Этот документ не открывает A1 и не даёт новых ALLOW. MP-3 baseline и exact compatibility остаются условиями выбора практической residual-ASK семьи. Q1 может завершаться независимо. Код защищённого исполнения, изменения смежных репозиториев и развёртывание не выполняются только на основании данного проекта.

Ближайшее локальное действие — [ограниченная инвентаризация среды](batch_interaction_local_preflight_ru.md). Она выясняет версии/пути и доступность одноразовой Linux-среды. Ручную синтетическую проверку консоли можно выполнить отдельно до полной интеграции, но вводит пользователь, а агент не использует PTY/scripted input вместо него. Получение ввода от полномочного процесса и участие физического человека остаются разными свойствами.

Сквозное исполнение и пакетирование ждут доверенной подготовки, закрытых обходов, устойчивой однократности и приёмки реального исполнения; успешный question-стенд не заменяет эти условия.
