## Практический приоритет после наблюдения 20.10.2026

В трёх Windows-запусках OpenCode 1.19.0 зафиксированы **193 записи `asking` (171 `bash`)** и отдельно **22 формы `question` / 25 пунктов**. Это **не** измеренные числа окон, ответов или ошибочных запросов. Цель — сократить **фактические прерывания человека**, не ухудшая завершение задачи и не снимая технических ограничений. Это рабочий порядок, **не** объявление закрытия прежних этапов.

| Приоритет | Действия | Gate / результат |
|---|---|---|
| P1 — достоверный baseline | Обезличенно связать типы native permission, формы Q, реально показанные окна и исходы; выяснить effective Windows 1.19.0 policy, активные источники моделей и разрешений | Отдельные числа для событий/UI/Q, version/platform/session coverage; без сырых команд или секретов |
| P2 — быстрое native-first сокращение | Найти проверенные безопасные семьи read/Git/диагностики, устранить лишние оболочки; оценить совместимость Windows и узкие правила, без широкой выдачи `bash` | Доказанный отрицательный корпус и сравнение идентичной работы до/после; №39, без нового production ALLOW до gate |
| P3 — поведенческая самостоятельность | Уточнить managed instructions: исправлять рутинные локальные ошибки самостоятельно, не повторять согласие продолжать; существенные Q собирать пакетом и разделять с разрешениями | Q2 после Q1, измерить качество и число **реальных** прерываний; №48 |
| P4 — модельные профили, параллельный design | M0/M1: проверить фактический model identity/route, модельную смену, saved `always`, subagents и критерии пригодности; спроектировать три уровня | [№53](https://github.com/dilukhin/opencode_permissions/issues/53), [дизайн](model_autonomy_profiles_design_ru.md); никакого повышения ALLOW |
| P5 — технический прототип | Только после M0/M1: M2/M3, узкие native/deterministic профили, пересечение с task/workspace/parent, отрицательные тесты Windows/Linux exact-version | `unsafe_automatic_allow=0`, `profile_bypass_count=0`; нет live установки |
| P6 — пользовательский пилот | Завершить MP-3 для нужной версии, провести Q2 и M4 на сопоставимых рабочих задачах, разрешая изменения конфигурации только явно | Реальные окна до/после, полнота работы, отказы/rollback, раздельные данные по профилям |
| P7 — расширение | M5: включить лишь доказанные точные семьи; A1/A2 — если штатного разрешения недостаточно; auditor — только при измеренной остаточной неоднозначности | Отдельное решение по gates, подтверждение отсутствия unsafe ALLOW |

P2 и исследовательские M0/M1 допускаются параллельно; **M4/новые profile-conditioned ALLOW не опережают MP-3, M2/M3 и согласование внедрения**. Модель не может сама выбрать или повысить свой профиль. Дешёвый дочерний агент не наследует расширенные полномочия родителя. Самая сильная модель не обходит hard DENY и границу agent-safe.

## Параллельное направление: минимизация вмешательств пользователя (#48)

Принята цель: уменьшать как запросы технических разрешений, так и вопросы агента; обеспечивать длительное самостоятельное выполнение в технически ограниченной области. [Проектирование и критерии](batch_interaction_design_ru.md).

- **Q0** (разрешено сейчас): зафиксировать дизайн пакетирования вопросов, использовать существующий `question` как кандидат для одного пакета из нескольких независимых решений; не выдавать ответ Q за техническое согласие.
- **Q1** (после Q0 review): изолированный exact-version runtime test с имитацией модели и `question.asked/replied/rejected`; без реальных моделей и без изменения production config.
- **Q2** (после Q1): пилот managed instructions и измерение реальных вопросов/остановок. Подключение инструкций — через `opencode_setup`/`agent-toolchain`, не прямым редактированием пользовательской конфигурации.
- **A0** (параллельное проектирование): [контракт](batch_approval_owner_contract_ru.md) расширяет существующего владельца из #46/PR #47; неизменяемый перечень, отдельные решения и допуска, частичный отказ, зависимости, подмена/повтор/авария. До пакетного исполнения закрыть доверенную подготовку одиночного вызова, прямые обходы и устойчивый барьер agent-safe; без второго владельца и новых `ALLOW`.
- **A1/A2** (после MP-3 baseline, exact-version revalidation и отдельного принятия): реализация только доказанного недостатка штатных разрешений, isolated/runtime проверки, затем opt-in и замер. Не расширять P0 по умолчанию.

Ручной ввод пользователя в защищённой консоли и наблюдение установленного OpenCode потребуют отдельного ограниченного локального задания. Текущую итерацию проектирования выполнить в Web; агент не может сам дать ответ вместо человека. Проверка консоли сама по себе не доказывает безопасное исполнение.

Ни один пункт не отменяет действующие Gate B/DC и MP-3, не разрешает `bash: allow` или self-approval. Проблема ADB/PowerShell `&` остаётся отдельной регрессией и не блокирует Q0/Q1.

## Параллельное направление: профили возможностей моделей (№53)

Принято требование: меньше самостоятельности у дешёвых/бесплатных/неизвестных моделей и больше у отдельно проверенных сильных. **Цена не подтверждает способность безопасно действовать.** [Проектируемые профили и испытания](model_autonomy_profiles_design_ru.md) различают свободу инженерных решений и технический потолок полномочий; пока это **design candidate** без назначения конкретных моделей и без новой policy.

- **M0** — проверить exact runtime binding выбранной/фактической модели, смену, fallback, дочерние агенты, ранние ALLOW и сохранённые разрешения Windows 1.19.0 / Linux 2.0.23; не считать upstream source доказательством пользовательской установки.
- **M1** — воспроизводимо оценить конкретные модели, защищённый пользовательский каталог категорий, default `restricted` для неизвестных; не делать назначения по цене или самозаявлению модели.
- **M2/M3** — только после M0/M1 спроектировать и проверить минимальные технические ограничения всей цепочки; сначала native + existing deterministic; отрицательные случаи без разрушительного выполнения.
- **M4** — после подтверждённых MP-3 и exact compatibility пользовательский пилот с явным opt-in; сравнивать фактические прерывания, качество и отказы для разных профилей.
- **M5** — после M4 принять или отклонить точечное расширение; интеграция и возврат настроек у `opencode_setup`/`agent-toolchain`.

Исходные baseline, Gate B/DC, отдельные Q/A, самостоятельность `agent-safe` в execution и trusted workspace остаются независимыми gates. Ни настройка имени агента, ни ответ `question`, ни сохранённый `always` не дают разрешения обойти профиль.

## Организация

- 2А → 4А → 4Б и 2Б → 5 — независимые направления, отдельные PR.
- Проектирование #34 начинается до окончательного утверждения соседних schemas. Реализация не должна опережать согласование input/source/consumer.
- Не дублировать installer в opencode_permissions; runtime recovery остаётся в agent-safe, transport — в ssh_relay.
- P0 не ждёт workspace trust, structured invocation или auditor.
- Producer workspace trust принят; следующим барьером первого P1 ALLOW служат MP-3 baseline и отдельная integration acceptance, а не доработка producer. Self-trust boundary готовить до нового ALLOW. Не смешивать эту работу с #34.
- Перед следующим implementation slice проверять HEAD/issues/PR владельца; сохранять параллельные изменения.
- GitHub Connector — основной транспорт; после записи targeted read-back.
- Локальный исполнитель нужен только для действительно локальной проверки, с ограниченным заданием.

## Проверки и ограничения

Изменение только документов не требует новых runtime опытов. Проверки существующего exact артефакта переиспользуются как evidence; они не доказывают новую реализацию или изменённую среду.
Новое разрешение требует regression case и проверки отсутствия unsafe ALLOW.
Реальное включение pilot не является побочным эффектом обычного apply/update.

Auditor, kernel broker по умолчанию, общие schemas без producer/consumer, расширение P0 на writes/remote/build/test и смешение transitional YC с P0 отложены.

Ближайший измеряемый результат: раздельный пользовательский учёт фактических вмешательств и ограниченный MP-3/Windows-native пилот; параллельно M0/M1 — без изменения полномочий. Для практического внедрения owner — [agent-toolchain#61](https://github.com/dilukhin/agent-toolchain/issues/61); модельные профили — [№53](https://github.com/dilukhin/opencode_permissions/issues/53). Mapping #34 остаётся самостоятельной задачей, не обязательным условием сокращения Q.
