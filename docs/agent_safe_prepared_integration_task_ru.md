## Цель и конкретная граница

Добавить узкое внутреннее подключение ExecutionPort к сохранённому восстановлению
и его verify. Сохранить один _run, журнал, ACTIVE и исходный INCIDENT_BLOCKED.
Не копировать policy/issuer в agent-safe. Поставляемая библиотека opencode_permissions
остаётся владельцем проекции, файловой кодировки и одноразового состояния.

Контракт реализован для общего доверенного Python-процесса. Пока реальный native host
не подключён, результат — проверяемая внутренняя интеграция на временных целях и
имитации host, **не** новый публичный управляемый CLI и не production-подтверждение.
Встроенный путь не должен сам создавать HostPort или автоматически вызывать approve_once.

## Действия

1. Выбрать явный внутренний managed-вход рядом с recover либо узкое необязательное
   подключение, которое устанавливает только доверенный код приложения. Ручной recover
   сохраняет совместимость. Если managed-вход выбран, отсутствие authority/ExecutionPort
   приводит к отказу; не переходить молча к ручному --approved.
2. До служебных записей требовать от доверенного host подтверждённый вход в recovery,
   охватывающий соответствующий журнал/барьеры. Этот внешний допуск не заменяет разрешения
   на process/verify. До подключения источника такого допуска публичный путь не включать.
3. Сохранить первоначальные PreparedProcess обеих ролей до mutation. В доверенном
   acquire(binding) сверить session/call/source/attempt/role с собственным контекстом,
   выполнить runtime preconditions и revalidate_process для первоначального снимка,
   затем получить свежий prepare_process. Нельзя возвращать сохранённый объект без проверки.
   Нельзя пересобирать первоначальную команду из свежих отличающихся фактов.
4. Получить отдельные CallBinding для process и verify с разными call_id. Через
   ExecutionPort.request получить ASK_USER или DENY. Доверенный владелец opencode_permissions
   обрабатывает штатное отдельное approve-once; агент, --approved и модель не подтверждают его.
   Для verify запрос допустим позже, чтобы не истёк TTL, но только по исходному снимку.
5. Перед каждым _run: проверить блокировку и применимые preconditions, затем
   ExecutionPort.consume. На успехе запустить именно исходный PreparedProcess один раз.
   Любая ошибка разрешения блокирует этот spawn. Не принимать JSON/string grant или
   callback вида lambda: True. Не реализовывать собственную stat-кодировку.
6. Сохранить consumed при not_started, failed, unknown и любом исключении после consume;
   не возвращать разрешение в очередь. При отмене вызвать HostPort.cancel через владельца,
   при завершении доверенной сессии — close. Новая попытка требует нового решения.
7. Обработать AuthorizationError отдельно. Если process уже выполнился, отказ разрешения
   verify означает незавершённую проверку, а не отсутствие восстановления. Сохранить
   evidence и блокировку; не повторять process ради получения verify.
8. Решить поставку зависимостей в этом узком библиотечном режиме: точная версия
   opencode_permissions, контролируемый путь импорта, отсутствие загрузки кода из cwd.
   Без поддержанного способа поставки оставить подключение внутренним тестируемым API.

## Разрешённый объём и запреты

Изменять только нужный код подключения recover, его тесты и документы. Добавлять
зависимость/пакетирование только в минимальном объёме для данного API. Не менять
содержимое opencode_permissions, не реализовывать публичные #25A-флаги заодно,
не добавлять SSH/daemon/helper, ALLOW для Python, автоматический rollback или retry.
Не трогать реальные устройства, серверы, облако и действующие разрешения OpenCode.

## Проверки на временных целях

- Настоящие PreparedProcess из prepare_process проходят библиотечную проекцию без
  ручной пересборки; argv/stdin/stat/artifact descriptors совпадают.
- ASK без события доверенного host, native DENY и --approved без managed authority:
  _run не вызывается. Изменение native на DENY после approve тоже запрещает запуск.
- Подмена argv/stdin/timeout, роли, source/attempt/call/session, executable/cwd/артефакта,
  включая замену теми же bytes: отказ до соответствующего spawn.
- Истёкший, отменённый, чужой или уже consumed объект не запускает процесс;
  одновременные потребления разрешают один запуск.
- Разрешение process не подходит verify. Отказ verify после успешного process сохраняет
  результат process и блокировку; повтор process не выполняется.
- Доказанная ошибка создания процесса не восстанавливает grant; unknown не повторяется.
- Старый ручной путь и точные stdin bytes остаются совместимыми; матрица Windows/Linux.

Сначала независимые проверки на настоящей библиотеке и временных целях, затем штатные
проверки репозитория и CI. Имитацию host явно отличать от настоящего OpenCode continuation.
Если реальное размещение требует межпроцессного канала, вернуть его точную схему
opencode_permissions для отдельной проверки; не заменять его файловым токеном.
