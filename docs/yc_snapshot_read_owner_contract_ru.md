# YC59: адресное чтение у существующего владельца согласия

Статус: исполняемый контракт и изолированные испытания. Рабочая установка,
новый ALLOW и новый артефакт этим изменением не разрешены.

## Путь запроса

`tools/yc_snapshot_read.py` соединяет проверяемое описание чтения с существующим
Ledger из #47. У владельца добавлены две функции, назначаемые **только доверенным
кодом запуска**: `canonicalizer` проверяет описание при регистрации;
`consume_check` повторно проверяет сохранённые байты перед однократным потреблением.
Это тот же автомат pending/approved/consumed/cancelled/expired, не новая таблица
допусков. Прежний профиль sudo-job остаётся поведением по умолчанию. Неизвестный
профиль не может молча обойти настроенный запрет по хешу команды.

Зависимость закреплена commit SHA и SHA-256 в `tests/yc59_windows/pins.json`.
Она остаётся испытательным кодом открытого черновика #47; успешные проверки
не означают принятия всего того PR или готовности production-поставки.

`ReadProfile` получает `ReadContext` от доверенного источника владельца и заново
строит точное описание. Проверка структуры dataclass **не удостоверяет источник**.
Источнику нужны независимо полученные сведения о выбранной ВМ/диске, каталоге
и облаке, собственная идентичность наблюдения и его время, отдельно выбранный
человеком ID снимка, факты установленного исполняемого файла и окружения.
Нельзя построить этот источник из заявления модели `trusted=true`.

| Что связывается | Сведения в неизменяемом описании |
|---|---|
| Запрос | session_id, call_id, host_id, версия политики |
| Цель | cloud/folder/VM/disk/snapshot ID, идентичность наблюдения, точное значение монотонных часов в hex |
| Исполнитель | платформа, абсолютный путь, идентичность файла, SHA-256, точная версия YC |
| Окружение | cwd, идентичности окружения и контекста учётных данных; секретные значения не передаются |
| Чтения | ровно instance/disk/snapshot get по exact ID, полный упорядоченный argv |
| Вывод | compute-rest-json/v1, общий срок 30 секунд, stdout 64 КиБ и stderr 8 КиБ на процесс |

Наблюдение исходной цели должно быть не старше 60 секунд и не из будущего.
Подтверждение не продлевает срок Ledger. Новая запись времени наблюдения меняет
описание; нельзя незаметно освежить прежнее согласие. Native DENY проверяется
при регистрации, при потреблении и перед каждым дочерним процессом.
Неизвестный/недоступный native источник останавливает профиль.

## Команды и представление ответа

Каждый из трёх getter имеет фиксированный хвост:

```text
--cloud-id C --folder-id F --format json-rest --retry 0 --no-user-output --no-browser
```

Это отдельный профиль с подтверждением, а не расширение общего allowlist.
В исходном A0 рассматривался `--format json`; здесь сознательно выбран
`json-rest`, чтобы не смешивать CLI snake_case и REST camelCase и использовать
готовую строгую проекцию. Официальные справочники подтверждают наличие
`json-rest` и `--retry 0`; реальный вывод **установленной** версии YC ещё не
наблюдался. Неизвестное/неподходящее представление отклоняется без преобразования
«по догадке». Чтение исходной ВМ включено в ту же область согласия, чтобы заново
сопоставить её подключение диска.

Модель не задаёт argv, дополнительные флаги, profile/endpoint/token, формат,
`jq`, перенаправление, программу, окружение или функцию запуска. Фиксированные
флаги поставляет владелец. Указанные cloud/folder не заменяют проверку ответа.
Отключение повторов CLI не означает доказательства ровно одного HTTP-запроса.

Источники, проверены 01.11.2026:

- [Snapshot.Get CLI: флаги, json-rest, отключение повторов](https://yandex.cloud/en/docs/cli/cli-ref/compute/cli-ref/v0/snapshot/get)
- [Compute CLI: глобальные флаги](https://yandex.cloud/ru/docs/compute/cli-ref/)

## Потребление и захват

`dispatch_read` вызывается внутри доверенного владельца, с SID из токена ОС.
Ledger проверяет вызывающего, digest, состояние, срок и повторный контекст,
затем атомарно потребляет согласие **до первого запуска**. Сохранённые байты
описания остаются внутри владельца. Иной потребитель не получает переносимый
токен запуска. Публичные JSON-поля `approved` и функции обратного вызова не
принимаются. Только выигравшее потребление начинает последовательность.

`tools/yc_read_capture.py` читает оба канала фиксированными порциями через
ограниченную очередь. stderr учитывается по объёму и отбрасывается. При превышении
лимита, ненулевом коде, ошибке запуска или тайм-ауте выдаётся фиксированный код,
сырой stdout/stderr не возвращается и не журналируется. Завершается только
дочерний процесс, переданный доверенной функцией запуска. Автоматического повтора
нет; согласие остаётся израсходованным даже при доказанном отсутствии запуска.

Общий срок относится к дочерним чтениям; завершение/очистка имеет отдельный
короткий предел. Профиль не поддерживает программу, порождающую потомков с
унаследованными pipe: незавершённая очистка даёт отказ. Установщик обязан
подтвердить этот контракт целевого YC и ограниченность самой функции запуска.
Этот компонент не является универсальным управлением деревом процессов.

Функция запуска принадлежит setup: точный проверенный путь, cwd, защищённое
окружение и credentials, stdin=DEVNULL, stdout/stderr=PIPE в двоичном режиме,
shell=False; повторная проверка файла/config непосредственно на границе запуска.
Путь/хеш в dataclass сами не устраняют файловую гонку и не защищают от root/SYSTEM.
Модуль не разрешает обращаться к скрытому downstream установленного guard.

Проекция появляется только после всех трёх успешных ответов и повторной проверки
контекста. При чужом sourceDiskId, каталоге, подключении диска, размере или
неподходящем JSON частичного результата нет. К существующим отметкам
`independent_guard_readback=false` и `restore_verified=false` не приписывается
достоверность облака, отсутствующая у синтетического источника.

## Windows и интерфейс владельца

Испытательный pipe-транспорт из #64 принимает эти функции только при создании
сервера. После чтения сообщения он получает SID через токен Windows. Тот же
недоверенный агент, которому закрыт decision pipe, запрашивает настоящее
потребление у Ledger; только затем сервер запускает синтетический источник JSON.
Заменённый снимок или новый DENY отменяет ранее подтверждённый запрос до запуска.

`tests/yc59_windows/review_read_request.py` — отдельная испытательная консоль
владельца. Она требует терминал, показывает экранированное точное описание,
digest и ограничения, запрашивает явную фразу с полным request UUID. Любой иной
ответ — отказ. Консоль записывает решение и не исполняет чтение. Pipe/PID должны
происходить из доверенного запуска. Сам признак TTY не доказывает человека.
Смена эпохи владельца или несовпадение квитанции не принимаются за успех.

В рабочей схеме **весь OpenCode и его плагины должны находиться под отдельным
SID агента**. Нельзя запускать их под SID владельца и объявлять эту консоль
защищённым каналом. Нет готовой установки этой схемы на DIMA-HP; сервисы,
учётные записи и настройки установленного компьютера не меняются.

## Проверки и оставшаяся приёмка

- Переносимые unit-тесты: точные команды и все привязки, свежесть, native veto,
  ограничения двух каналов, ненулевой код/тайм-аут, отсутствие сырого вывода,
  защитные условия консоли и явное решение.
- `test_read_owner.py --owner-core ...`: тот же закреплённый Ledger, реальные
  временные дочерние Python-процессы, отсутствие запуска до согласия, отзыв при
  дрейфе, гонка потребления, отсутствие частичной проекции и повторного запуска.
- Windows CI: отдельная реальная учётная запись, закрытый decision pipe,
  профиль YC, автоматическое решение владельца и три синтетических дочерних
  процесса. Это не запуск YC и не доказательство присутствия человека.

Остаются защищённая поставка/запуск обоих субъектов ОС, доверенное получение
ReadContext и native veto, проверенный потребитель функции запуска у toolchain,
точные версия/возможности установленного YC, реальное человеческое подтверждение,
content-bound артефакт и pin, управляемое обновление и установленный read-back.
До этого новые getters остаются ASK_USER, профили deployable не расширяются,
#59 и #55 не закрываются, изменения облака этим контрактом не разрешены.
