# Q1: стенд пакетных вопросов OpenCode

Q0 принят пользователем 13.10.2026; проектирование опубликовано в PR #49.
Q1 — проверка штатного инструмента question, без изменения рабочей установки или технических разрешений.

## Объект и способ проверки

Точный официальный OpenCode 1.19.0 на одноразовых Linux и Windows узлах GitHub Actions. Контрольные суммы архивов закреплены по release API в `tests/compatibility/question_1_19_0_assets.json`. Это испытательный перечень, а не новый разрешённый профиль compatibility registry.

Модель заменена локальным HTTP-сервером, который выдаёт точные tool calls. Настоящие question, permission, сохранение состояний инструментов и HTTP API OpenCode остаются неизменёнными. Ответы испытательного контроллера синтетические, не удостоверяют участие человека и не дают защищённых допусков.

Стенд использует уже применяемый в `tests/dc4_runtime/run_probe.py` способ локального OpenAI-compatible потока; разрешения и вопросы не имитируются. Отдельный наблюдатель подписывается на `/event` до начала сценария. Перед ответом проверяются pending request, sessionID, callID, messageID и сохранённый вход настоящего question. Ответы должны совпасть по числу и порядку.

Исходники проверены на теге v1.19.0: tool/question.ts, question/index.ts, question schema, HTTP routes, tool/registry.ts, tool/shell/id.ts и packages/core/src/flag/flag.ts. В этом теге shell сохраняет инструмент/permission key `bash`; question доступен при client=cli. Это наблюдения точной версии, не обещание совместимости следующих версий.

## Сценарии

| Сценарий | Проверка |
|---|---|
| batched | Один запрос с тремя вопросами, точные ответы, продолжение |
| sequential | Те же три вопроса последовательно, три запроса, продолжение |
| known | Сценарий без неизвестных решений не вызывает question |
| rejected | Отказ завершает question ошибкой, не создаёт ответы |
| cancelled | Abort завершает ожидающий инструмент без вымышленного ответа |
| controller_guards | Чужой сеанс, неверный порядок/число ответов отвергаются до отправки; запрос остаётся pending |
| question_not_grant_deny | После ответа Q штатный DENY сохраняется; безвредная echo-команда не исполняется |
| question_not_grant_ask | После ответа Q технический ASK остаётся pending; контроллер отдельно отклоняет его, исполнения нет |

Контроль самого наблюдателя: удаление asked из записанного потока должно давать INCONCLUSIVE, добавление повторного asked — FAIL. Эти контролируемые дефекты проверяют оценщик; они не выдаются за настоящий обрыв HTTP. Реальный обрыв/таймаут/неизвестная корреляция также не дают PASS.

PASS требует сопоставления событий с сохранёнными входами, metadata.answers, завершением инструментов и продолжением/остановкой сеанса. Отсутствие события само по себе не доказывает отсутствие запроса. Ошибка среды и неполное наблюдение завершают CI неуспешно с INCONCLUSIVE.

## Метрики и ограничения

Сравниваются question_request_count и question_item_count. Условия стенда: одинаковые три вопроса, одинаковые ответы, одна платформа и версия; ожидается 3 → 1 запрос. request_interruption_surrogate — испытательный суррогат, user_interruption_count остаётся null. Число реальных окон, время самостоятельной работы и качество планирования настоящей модели здесь не измеряются.

known проверяет только заданный сценарий без question. Он не доказывает, что настоящая модель научилась устранять ненужные вопросы. deny/ask проверяют отсутствие переноса полномочий в штатный механизм, не безопасность внешнего владельца из PR #47.

Q1 не закрывает MP-3, совместимость всей permission policy, Q2-пилот или A1. Реестр развёртывания и P0-артефакты не меняются. Публичный отчёт содержит лишь агрегаты, статусы и безопасные причины; журналы сервера, локальные пути и пользовательские ответы не публикуются.

## Запуск

На одноразовом испытательном узле:

```text
python tests/compatibility/download_question_binary.py --directory .q1-bin
python tests/compatibility/run_question_probe.py --opencode .q1-bin/opencode --output q1-report.json
```

Windows использует `.q1-bin/opencode.exe`. Рабочий OpenCode и его конфигурацию не обновлять ради этого опыта. Общий CI выполняет проверки на обеих платформах и сохраняет отдельные обезличенные отчёты.

После PASS Q1 следующий шаг — ограниченный Q2-пилот через владельца установки: одинаковые реальные задачи до/после, прямой счёт вмешательств человека и анализ ошибок/лишних вопросов. Подготовку одиночного защищённого допуска можно вести независимо; пакетирование A не включать до его приёмки.
