# Длительный sudo-job с DIMA-HP: точная граница OpenCode 1.19.5

Дата: 04.11.2026. Связано с #46/PR #47, agent-safe#36/PR #37, ssh_relay#52.
Статус: **кандидат маршрута, производственный допуск не разрешён**.

## Подтверждённые исходные версии

- На DIMA-HP сообщена версия OpenCode **1.19.5** (Windows 10). Это заявление о локальной установке; независимое чтение самой DIMA-HP не проводилось.
- Исходники OpenCode v1.19.5: `anomalyco/opencode@810c0eba1a7348036f8bdf61e6632d0c36c6876c`. Архив Windows x64 имеет опубликленный испытательный SHA-256 `09a6e693157f0887e504f2cf4357a8cbddc5ead5d0dffb9a269dcc47c48640f5`, контролируемый файлом `tests/compatibility/yc59_native_1_19_5_pins.json` в `opencode_permissions/main@8aa08878a285371ccec55b3c84c0950543dcd3e9`.
- `ssh_relay/main@48c9cd968d7edf1e68d08abf3d308f5abf1bebd6`: транспорт Windows → Linux по прямому SSH либо через проверенного посредника, с проверкой отдельных host keys. `sudo-job` требует Linux/systemd-узел. Прошедший маршрут DIMA-HP → aragorn через vserv не является приёмкой Windows → одноразовая Ubuntu → sudo-job с доверенным разрешением.
- `agent-safe/PR#37@032cd02856c6ac076853042b785904b95a72adaf`: жизненный цикл start/observe/unknown и read-only verify; тестовый `approved=True` не является происхождением разрешения человека.
- `opencode_permissions/PR#47@6ddac8d8a29c5c660fd373d9b2caa08735ed7a51`: Linux-прототип отдельного владельца, точная операция и одноразовое потребление. В production CLI не подключён, решение в памяти не связано атомарно с исполнением.

## Граница доверия

Весь OpenCode, включая Shell, плагины и ответы native permission API, считать **недоверенной стороной**. Положительный native once — только сообщение внутри OpenCode, не полномочие для root.

Рабочий владелец разрешений должен:
1. Жить под отдельной защищённой учётной записью, а на Windows — в другом интерактивном сеансе. Проверять фактические SID и TokenSessionId, а не поданные агентом значения. Временный Windows CI-стенд доказывает только отдельный процесс и границу ACL; ввод человека и отдельные сеансы на DIMA-HP не проверены.
2. Самостоятельно готовить точный argv/executable/cwd, сверять policy, команду UTF-8/SHA-256, job_id, transaction_id, SSH host key, адрес, пользователя, daemon instance и connection generation. Нельзя принимать сообщённую агентом identity как достоверную.
3. Держать root-enabled relay и его секреты за этой границей. Клиент OpenCode не должен иметь альтернативного прямого sudo-job API в обход владельца.
4. До отправки start устойчиво фиксировать единственное потребление и открытый safety-барьер. При сомнительном ответе — только чтение status/verify той же операции, без повторного start.
5. Отдельно подтверждать stop; устаревшего PID недостаточно, stop не закрывает unknown автоматически.

## Ограниченный опыт GitHub Actions

`.github/workflows/sudo-job-windows-1195.yml` проверяет настоящий OpenCode 1.19.5 с верификацией архива и native allow/deny/once/reject. Затем проверяет запреты недостаточно разделённой Windows identity. Использует одну временную машину `windows-latest` и неизменяемый baseline; персональные машины и VPS не затрагивает. Это **не** подтверждение конечного пути и **не** ввод человека.

Тройной опыт `agent-safe/.github/workflows/sudo-job-integration.yml` проверяет на одноразовом Ubuntu транспорт по точному SHA ssh_relay и автомат согласия по точному SHA этого PR, но допускает реальный sudo-job через испытательный `approved=True`. Прохождение не означает production admission. Один общий CI без связанного доверенного выполнения нельзя считать завершением #46/#36/#52.

## DIMA-HP: безопасная проверка перед приёмкой

В обычном `cmd.exe` без повышения прав, только чтение:

```bat
opencode --version
toolchainctl --version
toolchainctl check
safe --help
ssh_relay --version
ssh_relay doctor
where opencode
where toolchainctl
where safe
where ssh_relay
```

Ожидать именно 1.19.5 или остановить аттестацию версии. Команды `sudo-job start` и `stop`, `safe ... --approved`, включение P0 и изменение OpenCode permissions до завершения защищённого допуска **не выполнять**.

Для выбранной границы Windows отдельно, без создания новых пользователей автоматом, нужны фактические токены агента и владельца с разными SID и **разными интерактивными SessionId**. Если отдельный вход владельца не подготовлен, точный маршрут с DIMA-HP пока не подтверждён.

## Что обновляет toolchainctl

`toolchainctl update --apply` обновляет установленное ядро `agent-toolchain` из его `main`, затем выполняет `toolchainctl apply`. Через текущий ToolSpec он разрешает и устанавливает **текущие основные ветки** `agent-safe/master` и `ssh_relay/main` в управляемых окружениях, включая их навыки OpenCode; также обрабатывает прочие объявленные инструменты (включая tunnelctl и proxy-tools), конфигурацию и собственные управляемые файлы. Это **не** означает включение чернового PR, прототипа владельца или реестра `opencode_permissions`, не создаёт защищённый Windows-сеанс и не обновляет запущенный ssh_relay daemon без отдельной процедуры.

Следовательно, выполнять `toolchainctl update --apply` **с целью включения sudo-job до слияния и ручной приёмки бессмысленно**: основные ветки не содержат новой интеграции. Перед возвратом к MN-02 необходимы полный конечный тест доверенного решения на одноразовой Ubuntu, отдельная ручная приёмка Windows и опубликованная процедура установки владельца. Пока `native_sudo_job_admission_ready=false`.

Никаких изменений DIMA-HP, v7 и других пользовательских серверов этим документом не производится.
