# Учёт одноразового согласия sudo-inspect: испытательный этап #57

Статус: **только модель и проверки на искусственных данных**. Нет рабочего
владельца разрешений, CLI/IPC, grant, запуска SSH/sudo или подключения к OpenCode.
Файлы реализации находятся в `tests/`, не в production runtime.

Зависимости: [#57](https://github.com/dilukhin/opencode_permissions/issues/57),
[ssh_relay #58 / PR #59](https://github.com/dilukhin/ssh_relay/pull/59),
[agent-safe #38](https://github.com/dilukhin/agent-safe/issues/38).

## Зачем нужен этот этап

В существующем испытательном владельце [PR #47](https://github.com/dilukhin/opencode_permissions/pull/47)
согласие хранится в памяти. Однократное потребление проверено внутри одного
процесса, но его недостаточно для будущего запроса с привилегиями, если ответ
потерян или владелец завершился. Новый этап проверяет только устойчивое хранение
факта согласия и его потребления до передачи операции исполнителю.

Он не создаёт второго владельца решения и не меняет длительные sudo-job.
`tests/privileged_inspect_journal_fixture.py` — кандидат backend для будущей
интеграции с защищённым владельцем #47, а не копия его IPC/консоли/политики.
Существующая Gate B state model остаётся моделью authorization semantics;
новые тесты дополняют её настоящими транзакциями SQLite и несколькими процессами.

## Граница ответственности

Здесь учитывается только authorization:

```text
pending -> approved -> consumed
pending -> rejected
pending/approved -> cancelled | expired | invalidated
```

`consumed` — конечное состояние права, **не результат исполнения команды**.
Журнал не хранит состояния succeeded/failed/unknown операции, не выполняет
verify, recovery или cleanup. Владельцем этих механизмов остаётся agent-safe.
После неизвестного результата новый transaction ID запрещает именно safety-барьер
agent-safe и доверенный владелец. Одна таблица уникальных UUID не блокирует
создание caller-controlled новой транзакции и не решает этот вопрос сама.

Этот отдельный привилегированный сценарий учитывает подтверждённый обход
согласия через child/plugin и прежний root-enabled relay. Он не превращает
усиленную OS-изоляцию в новое требование default permission-пути проекта.

## Проверяемое связывание

В записи находятся только:

- канонический UUID транзакции;
- SHA-256 полного неизменяемого описания операции;
- SHA-256 ревизии policy, участвующей в решении;
- абсолютный deadline в миллисекундах UTC, не более 60 секунд при резервировании;
- поколение владельца и состояние согласия.

Полное намерение формирует и перепроверяет будущая доверенная сторона. Кандидат
профиля ssh_relay включает точный probe/argv/лимиты, session, восемь SSH pins,
identity транспорта, transaction и deadline. Backend получает уже вычисленный
digest: он не повторяет каталог команд и **не доказывает**, что переданные bytes
валидны или факты приобретены доверенно. Смена любого существенного поля должна
изменять digest; смена policy также отклоняет использование старой записи.

Сырые команды, адреса, SSH identity, stdout/stderr, credentials и полные намерения
в БД не сохраняются. Согласие на точные сохранённые bytes должно проверяться
защищённым владельцем до вызова backend; эти bytes остаются в его доверенном
контуре. После restart они автоматически не восстанавливаются из digest.

## Транзакции и перезапуск

Для перехода SQLite выполняет `BEGIN IMMEDIATE`; состояние и authorization audit
записываются одной транзакцией с `synchronous=FULL`. Успешный возврат `consume`
допустим только после COMMIT. Подтверждённый учёт не разрешает саму SSH-команду.

Есть три раздельных операции открытия:

1. `create` — явное создание нового испытательного файла через O_EXCL; существующий
   файл не перезаписывается, при ошибке он не удаляется для повторной попытки.
2. `attach` — дополнительное соединение того же владельца. UUID поколения —
   метаданные согласованности, **не credential и не аутентификация**.
3. `restart` — атомарная смена поколения и инвалидирование всех pending/approved.
   Старые handles становятся недействительными; consumed и другие конечные
   записи сохраняются. UUID транзакции нельзя использовать заново в любом состоянии.

Открытие существующего хранилища использует `mode=rw`: потерянная БД не создаётся
заново. Повреждение/неизвестная схема не запускают repair. На quota новые записи
отклоняются; прежние свидетельства потребления не удаляются ради освобождения места.
Постоянная очистка/архивирование и порядок изменения quota этим этапом не вводятся.

Deadline проверяется при решении и потреблении. Ранее замеченное время сохраняется;
обратный скачок часов блокирует переход и restart. Время получает доверенный
владелец; callback в fixture нужен для воспроизводимых тестов и не передаётся агенту.

Ошибка записи/COMMIT не выдаёт положительного результата, текущий handle блокируется.
Если COMMIT уже состоялся, а ответ потерян, новое соединение видит consumed.
Если транзакция откатилась, запись может остаться approved: **другой handle того же
поколения технически способен её потребить**. Поэтому будущий владелец обязан
остановить все свои execution-продолжения после storage uncertainty; одного
локального флага fixture недостаточно. Новый защищённый запуск инвалидирует
неиспользованные согласия. Исполнитель до подтверждённого потребления не вызывается.

## Что доказано тестами

- запись состояния и audit видна другому соединению до возврата потребления;
- один победитель среди отдельных соединений в потоках и среди отдельных процессов;
- pending/reject/cancel/expiry, повтор и изменение binding не потребляются;
- consumed сохраняется после открытия и restart; unused согласия не оживают;
- аварийный выход процесса после COMMIT не позволяет повторить потребление;
- потеря ответа COMMIT, отказ audit insert, quota и повреждение/отсутствие БД
  не маскируются положительным результатом;
- raw намерение и данные root-проверки отсутствуют в дампе таблиц.

Это тесты логической устойчивости на временной локальной SQLite. Они не доказывают
сохранность при отключении питания, правильность fsync/VFS/сетевой файловой системы,
неизменяемость БД от её владельца или OS-защиту от другого процесса. У audit нет
внешнего доверенного anchor; доступ к файлу позволяет подменить историю.

## Что ещё требуется до рабочего допуска

1. Переиспользовать защищённый owner из #47, проверить недоступность его decision
   API и хранилища всему OpenCode, включая плагины. Размещение/права, peer identity
   и защита кода/credentials проверяются отдельно. Права O_EXCL/0600 в fixture
   не доказывают защищённость каталога, отсутствие symlink/TOCTOU или Windows ACL.
2. Связать реальное решение человека и native DENY с конкретным намерением.
   `record_decision(..., 'approve')` доступен тестовому процессу и не является
   человеческим согласием. Нельзя экспортировать этот API недоверенному агенту.
3. Приобрести и повторно проверить фактические SSH pins/transport identity/policy
   внутри доверенного владельца; выполнить точную проекцию профиля из ssh_relay.
4. Согласовать порядок durable consumption с барьером agent-safe до отправки,
   включая аварии между двумя хранилищами, неизвестный ответ и запрет новой транзакции.
   Атомарность SQLite не обеспечивает exactly-once удалённое исполнение.
5. Только затем подключать inspect-only executor/нормализатор и проверять отдельный
   сквозной сценарий на одноразовом Linux-хосте. Пользовательские VPS и почта исключены.

Ни production policy, ни compatibility registry, ни существующий OpenCode runtime
не меняются. #57/#58/#38 не закрываются; новый PR остаётся черновым без merge/deploy.
