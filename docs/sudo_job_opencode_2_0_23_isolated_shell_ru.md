# Опыт изоляции Session.shell по Linux UID

Связано с ssh_relay#52 и opencode_permissions#46, PR #47.

## Вопрос и ограничение

В предыдущем опыте реальный child OpenCode 2.0.23 смог ответить `once` за интерфейс в default и stdio. Следующий опыт проверяет только один вариант устранения этого канала: сервер и команды Shell работают под разными Linux UID, а среда команд не содержит credential API.

Upstream остаётся точным 0fd7e2829449b052abf0078666669302923d77af. Его исходники и API не изменяются. Через штатный выбор SHELL передаётся отдельная испытательная оболочка. Это изменённая конфигурация execution host, а не штатная защищённость установленного OpenCode. Сборка по-прежнему без встроенного веб-интерфейса.

## Испытательная конфигурация

- Режим: одноразовая Linux CI fixture, без SSH, VPS, установок удалённых пакетов и пользовательских команд.
- Сервер работает как непривилегированный daemon UID; команды — как отдельный nobody UID. Учётные записи не создаются и не изменяются. Дополнительные группы команд очищаются, `no_new_privs=1` проверяется в реальном child.
- Root launcher существует только внутри опыта. Он принимает соединения Unix socket от host UID, проверяет SO_PEERCRED и запускает команду исключительно под заранее заданным tools UID. Он не принимает UID, окружение, имя root-команды или решение о согласии от caller.
- Все изменяемые файлы принадлежат временному каталогу fixture. Личный каталог сервера имеет mode 0700; отдельный синтетический файл — mode 0600. Project доступен обоим UID только для обмена результатом.
- Команда запускается настоящим Session.shell. Передаются только адрес loopback сервера, PID созданного сервера, synthetic session/request ID и пути объектов fixture. Пароль не передаётся в argv. Launcher выдаёт командному процессу только PATH, HOME и кодировку.
- Child проверяет свою среду, `/proc/PID/environ` только созданного сервера, доступ к синтетическому private-файлу, доступ к socket launcher и ответ API без аутентификации. Другие процессы и секреты не исследуются.

Ожидается: tools UID подтверждён, дополнительных групп нет, no_new_privs включён; пароль недоступен; чтение серверного /proc/private-файла и соединение с launcher запрещены; ответ API без аутентификации — 401; pending request остаётся до отдельного scripted reply испытательного owner. Проверки once/replay/reject/deny/stop из предыдущего опыта выполняются снова в обеих конфигурациях.

При неожиданном результате workflow завершается с ошибкой и не включает допуск. Raw evidence сохраняется только во временном CI artifact вне репозитория. В журналы выводятся булевы итоги, без паролей и authorization headers.

## Что этот опыт не доказывает

Изоляция только Shell не ограничивает Read/Write, MCP, PTY или плагины внутри серверного процесса. PluginHost по исходникам имеет прямой permission.reply. Root launcher не является broker человеческого согласия и не выпускает grant. Настоящего нажатия в интерфейсе и сквозного допуска sudo-job здесь нет. Windows и service mode не проверены.

Даже успешный результат оставляет `native_sudo_job_admission_ready=false`, реестр 2.0.23 закрытым, PR #47 и agent-safe#37 черновыми. Для полного решения нужны защищённый источник решения, изоляция всех недоверенных исполнителей, привязка решения к неизменяемой операции и одноразовое атомарное потребление до запуска.

## Состояние до CI

Python-файлы проходят py_compile. Локальный self-check в Web остановился на chown с EINVAL: эта среда не поддержала требуемую смену владельца на выбранный системный UID. Локальный опыт не считается успешным. Проверка Linux fixture и настоящего OpenCode выполняется в отдельном шаге CI; результат будет зафиксирован по точному HEAD.
