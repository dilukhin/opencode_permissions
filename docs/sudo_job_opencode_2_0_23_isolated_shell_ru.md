# Опыт изоляции Session.shell по Linux UID

Связано с ssh_relay#52 и opencode_permissions#46, PR #47.

## Вопрос и ограничение

В предыдущем опыте реальный child OpenCode 2.0.23 смог ответить `once` за интерфейс в default и stdio. Следующий опыт проверяет только один вариант устранения этого канала: сервер и команды Shell работают под разными Linux UID, а среда команд не содержит credential API.

Upstream остаётся точным 0fd7e2829449b052abf0078666669302923d77af. Его исходники и API не изменяются. Через штатный выбор SHELL передаётся отдельная испытательная оболочка. Это изменённая конфигурация execution host, а не штатная защищённость установленного OpenCode. Сборка по-прежнему без встроенного веб-интерфейса.

## Испытательная конфигурация

- Режим: одноразовая Linux CI fixture, без SSH, VPS, установок удалённых пакетов и пользовательских команд.
- Сервер работает как непривилегированный daemon UID; команды — как отдельный nobody UID. Учётные записи не создаются и не изменяются. Дополнительные группы команд очищаются, `no_new_privs=1` проверяется в реальном child.
- Root launcher существует только внутри опыта. Он принимает соединения Unix socket от host UID, проверяет SO_PEERCRED и запускает команду исключительно под заранее заданным tools UID. Он не принимает UID, окружение, имя root-команды или решение о согласии от caller.
- Все изменяемые файлы принадлежат временному каталогу fixture. Личный каталог сервера имеет mode 0700; отдельный синтетический файл — mode 0600. Project доступен обоим UID только для обмена результатом.
- Команда запускается настоящим Session.shell. Передаются только адрес loopback сервера, PID созданного сервера, synthetic session/request ID и пути объектов fixture. Пароль не передаётся в argv. Launcher выдаёт командному процессу только PATH, HOME и кодировку.
- Child проверяет свою среду, `/proc/PID/environ` только созданного сервера, доступ к синтетическому private-файлу, доступ к socket launcher и ответ API без аутентификации. Другие процессы и секреты не исследуются.

Ожидается: tools UID подтверждён, дополнительных групп нет, no_new_privs включён; пароль недоступен; чтение серверного /proc/private-файла и соединение с launcher запрещены; ответ API без аутентификации — 401; pending request остаётся до отдельного scripted reply испытательного owner. Проверки once/replay/reject/deny/stop из предыдущего опыта выполняются снова в обеих конфигурациях.

При неожиданном результате workflow завершается с ошибкой и не включает допуск. Raw evidence сохраняется только во временном CI artifact вне репозитория. В журналы выводятся булевы итоги, без паролей и authorization headers.

## Что этот опыт не доказывает

Изоляция только Shell не ограничивает Read/Write, MCP, PTY или плагины внутри серверного процесса. PluginHost имеет прямой permission.reply. Root launcher не является broker человеческого согласия и не выпускает grant. Настоящего нажатия в интерфейсе и сквозного допуска sudo-job здесь нет. Windows и service mode не проверены.

Даже успешный результат оставляет `native_sudo_job_admission_ready=false`, реестр 2.0.23 закрытым, PR #47 и agent-safe#37 черновыми. Для полного решения нужны защищённый источник решения, изоляция всех недоверенных исполнителей, привязка решения к неизменяемой операции и одноразовое атомарное потребление до запуска.

## Подтверждённая изоляция Shell

На opencode_permissions@0d0dbcd38e1c75dee0935262765ef6ca777b4940 [CI-опыт](https://github.com/dilukhin/opencode_permissions/actions/runs/37780904935) завершился успешно. [Общая матрица](https://github.com/dilukhin/opencode_permissions/actions/runs/37780904829) также успешна: все семь заданий.

В обычной синтетической конфигурации повторно получено child_can_reply=true для default и stdio. В изолированной конфигурации настоящий child Session.shell получил UID 65534, нулевой список дополнительных групп и no_new_privs=1. Проверки отсутствия credential, недоступности /proc сервера, private-файла и launcher socket, ответа 401 без authentication прошли. Child не смог ответить once в обоих режимах; pending request сохранился до scripted reply испытательного owner. В журнале: child_can_reply=false и child_proc_readable=false для default и stdio.

Это подтверждение ограниченных проверенных каналов, а не полной защищённости OpenCode. На первой ревизии опыта self-check создал каталог с mode 0755; configure теперь явно устанавливает 0700 и для уже существующих каталогов. Проверки не ослаблены.

## Следующий опыт: загруженный плагин

Fixture `reply_plugin.js` подключается через штатную конфигурацию plugins к тому же собранному CLI. В setup регистрируется permission evaluate hook, реагирующий исключительно на synthetic probe.plugin.reply. По ID синтетического pending request он вызывает настоящий context.permission.reply с decision=once. Пароль API не передаётся плагину и не читается им: проверяется прямое полномочие PluginHost.

Испытательный owner создаёт pending request и отдельным вызовом запускает hook. Принятый reply должен удалить именно этот request; другая session и replay должны быть отвергнуты. Configured deny самого trigger проверяется до hook: синтетический request должен остаться, файл наблюдения плагина не должен измениться. Сам trigger всегда получает deny и ничего не исполняет. Все операции остаются синтетическими, без удалённых мутаций и без объявления API-вызова согласием человека.

Если загруженный плагин смог ответить, изоляция Shell не устраняет канал расширений. Такой плагин должен считаться частью доверенного сервера либо исполняться за отдельной границей без права выдачи согласия. Результат новой проверки устанавливается по её точному HEAD; успех предыдущего Shell-опыта не переносится на неё автоматически.

## Локальная граница проверки

Python-файлы проходят py_compile. Локальный self-check в Web остановился на chown с EINVAL: эта среда не поддержала требуемую смену владельца на выбранный системный UID. Локальный опыт не считается успешным; приведённые выше результаты получены в Linux CI.
