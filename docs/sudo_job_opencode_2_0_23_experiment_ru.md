# Испытательный допуск OpenCode 2.0.23

Дата: 08.10.2026. Связано с #46, PR #47 и ssh_relay#52.

## Цель и граница результата

Проверить реальную реализацию ожидания разрешений и доступ дочернего процесса к API ответа, прежде чем выбирать доверенное продолжение для sudo-job. SSH, sudo и рабочие серверы в опыте не используются. Успешный workflow подтверждает выполнение опыта, но не готовность допуска: поле `native_sudo_job_admission_ready` всегда остаётся false.

Точный upstream: anomalyco/opencode@0fd7e2829449b052abf0078666669302923d77af, версия 2.0.23, Bun 1.4.2 и исходный frozen lock. Собирается CLI без встроенных веб-ресурсов; это испытательная сборка исходников, а не подтверждение идентичности установленного пользователем официального бинарного файла. В evidence записываются SHA-256 собранного файла и lock.

## Опыты

1. Файл `tests/opencode_2_0_23/permission_boundary.test.ts` помещается в test-каталог точного upstream Core после сборки CLI. Он использует настоящий Permission.Service, Agent, Database, Bus и SessionStore. Проверяет ожидание `assert`, одноразовое продолжение, отказ, configured deny, отмену вызова, закрытие host и отдельное разрешение stop. Исполнение представлено только добавлением значения в локальный массив. Подтверждение через Service.reply является испытательным вызовом API, а не согласием человека.
2. `run_boundary_probe.py` запускает собранный CLI в default и stdio. Каждый сервер получает новую изолированную HOME/config/project и только синтетический пароль. Проверяются отказ без authentication, владение request своей session, reject/deny, повтор ответа, отдельный stop и отсутствие сохранённого разрешения.
3. Child запускается через настоящий `Session.shell` OpenCode. Ему передаются URL, PID испытательного сервера, session/request ID и путь результата, но не пароль. Он проверяет только две переменные credential в своей среде и первоначальную среду созданного испытательного сервера в `/proc/PID/environ`. Другие процессы, реальные credentials и файловые хранилища секретов не читаются. Затем пробует ответить `once` на синтетический pending request другой session в том же проекте.

Читаемость `/proc` и принятие ответа фиксируются отдельными фактами. Удаление переменных из process.env само по себе не доказывает недоступность первоначальной среды процесса. Наличие ответа 204 проверяется также исчезновением того же request из pending list.

## Что остаётся вне опыта

- Настоящее подтверждение человеком в интерфейсе.
- Полный испытательный набор для service mode, Windows и установленного официального бинарного файла.
- Выполнение через недоверенное расширение: доступ PluginHost к permission.reply уже обнаружен при проверке исходников, но здесь не выдаётся за runtime proof.
- Доверенный внешний посредник, допуск agent-safe и сквозная удалённая установка.

Если child может ответить за пользователя, прямое native-разрешение в этом режиме не принимается как доверенный источник допуска sudo-job. Следующий этап должен установить технически защищённую границу. Если child не смог ответить, это подтверждает только проверенные каналы, а не отсутствие всех путей подделки.

Реестр совместимости 1.18.x и рабочая permission policy не меняются. Пароли, authorization headers, сырые server logs и команды пользователей не включаются в evidence.
