# Цикл обратной связи и качество повседневной работы OpenCode

Статус: методика для review; без нового ALLOW, конфигурационных изменений, включения пилота или приёмки установленного OpenCode.

Координация программы — [agent_control_plane #8](https://github.com/dilukhin/agent_control_plane/issues/8). Общий документ после публикации: `agent_control_plane/docs/agent_experience_improvement_program_ru.md`; точную предлагаемую ревизию смотреть в #8. Владельцы: [#39](https://github.com/dilukhin/opencode_permissions/issues/39) — Windows; [#48](https://github.com/dilukhin/opencode_permissions/issues/48) — вмешательства; [agent-toolchain #61](https://github.com/dilukhin/agent-toolchain/issues/61) — пользовательский цикл. #34 сохраняет только соответствие фактической операции авторизации. Профили #53 — отдельное последующее направление.

## 1. Пользовательская проблема

Частые формальные запросы на обычные действия превращают Allow always в механическое действие. Требуется снижать бессмысленные вмешательства, а не принуждать пользователя анализировать каждый shell-вызов. Это не обвинение модели: запрос создаёт исполнительный фреймворк, и модель может не видеть UI.

YC G1–G4 — узкий выпуск. Его завершение не означает готовность общей политики Python/PowerShell/Git или всего Windows-workflow. Эта документационная итерация не принимает G3/G4. Реальный следующий пилот требует собственного допуска, фактической версии и закрытого относящегося к нему gate.

## 2. Действующие границы

Native deterministic rules → deterministic parser/effect analysis → optional auditor только для доказанной residual gray zone → ASK_USER. DENY приоритетен; unknown не ALLOW; аудитор не исполняет команды и не отменяет запрет.

Не допускаются blanket bash allow, разрешение python/powershell по имени, автоматические клики Always, --auto и промптовые обещания вместо технических ограничений. Оценивается вся операция, включая вложенные интерпретаторы, compound/remote effects, пути и secrets.

Предпочитать эквивалентные штатные read/glob/grep. Узкий validator или structured operation рассматривается лишь при реальном gap и имеет собственный target/scope/effect contract. Проверка JSON с PASS/FAIL — пример кандидата, не уже установленный инструмент и не разрешение читать secret-like files.

## 3. Пять разных видов наблюдений

| Вид | Источник | Ограничение |
|---|---|---|
| Permission request / decision | Фактический permission-компонент OpenCode | Server event не обязательно видимое окно |
| Видимое окно / выбор пользователя | Проверенный UI-источник или ограниченное ручное наблюдение | Не угадывать по самоотчёту модели |
| Рабочий вопрос агента | Question-инструмент / история вызовов | Не техническое согласие |
| Safety/guard confirmation | Соответствующий runtime | Не обычный необоснованный ASK |
| Ошибка/повтор/исход утилиты | Компонент, наблюдающий исполнение | Различать not_started/known failure/partial/unknown |

Каждый счётчик имеет источник, область, методику и покрытие. Ненаблюдаемое unknown, не 0. Не объявлять все ASK ошибочными или все ответы пользователя доказанным согласием. История Always и effective overrides важны для сравнения.

## 4. Метрики и знаменатель

Считать вмешательства на сопоставимую задачу; события разрешений и вопросы отдельно; ошибки и повторы на число подходящих операций; полноту/успешность работы; длительность без вмешательства; дополнительные вызовы, время и стоимость при наличии источника.

Нужно учитывать удачные операции хотя бы агрегатно. Пустой журнал при неизвестной нагрузке не означает качество. Заявление «задача выполнена» не заменяет проверку результата; успешное исполнение не доказывает безопасность всей семьи.

Кандидат двукратного снижения остановок не является уже достигнутым или обязательным числом. Первый результат — хотя бы одно достоверное полезное улучшение при сохранении `unsafe_automatic_allow = 0` в проверяемом опасном корпусе. Это критерий тестов, не математическая гарантия всех будущих команд.

## 5. Сопоставимое измерение до/после

Перед началом фиксировать фактические platform/shell/OpenCode version, policy artifact/revision, effective permission layers, рабочую область, model/route только при доказанном источнике, задачу и метод подсчёта. Старые Windows 1.x/Linux 2.x наблюдения не являются версией текущей машины.

Не стирать пользовательскую конфигурацию или сохранённые разрешения ради чистого опыта. Не выбирать Always для улучшения цифр. Загрязнение исходными разрешениями отражать как ограничение; заранее согласованная изолированная среда допустима. Независимые Windows/Linux результаты не смешивать как численное до/после.

Один узкий фактор меняется за цикл. Сравнивать одинаковый класс/объём работ и проверять completed outcome. Повторное выполнение может менять кэш и знакомство модели с задачей; учитывать порядок, повторяемость и ограничения причинного вывода. Несопоставимые данные публикуются как наблюдения, не доказанный выигрыш.

## 6. Первый ограниченный сценарий

После явной приёмки нужного gate выбрать одну реальную рутинную задачу в разрешённом workspace. Предпочитать чтение/поиск/проверку формата несекретного файла либо другой действительно частый воспроизводимый безопасный класс. Не фиксировать заранее старую версию OpenCode и не откатывать установленную ради теста без отдельного решения.

Локальный агент получает exact paths/allowed commands/report/stop conditions только для локально необходимых наблюдений. Он не меняет архитектуру, global config, native policy или toolchain скрыто и не имитирует согласие пользователя. Web выполняет анализ, проектирование узкого изменения и GitHub review.

Один цикл: baseline → один кандидат → позитивные и отрицательные fixtures → проверяемый артефакт точной совместимости → отдельно разрешённое применение через владельца установки → read-back effective state → сопоставимое наблюдение → вывод.

До допуска реального применения можно завершить документацию/fixtures. Ошибка инструмента или неизвестный исход останавливает affected path, не вызывает обход оболочкой/encoding/другим транспортом и не запускает слепой повтор.

## 7. Переход от наблюдения к правилу

Высокая частота ASK даёт приоритет исследованию, не ALLOW. Пользовательский Always не является label «безопасно». Для нового правила проверить точный target, полный argv/payload, эффекты и соседние опасные формы. Не распространять узкую read-only удачу на общий интерпретатор.

Типовые отрицательные случаи: соседний secret-like path, external directory/reparse, лишний параметр, redirect/pipe/compound, nested interpreter, remote target, drift операции после согласия, неизвестная версия/профиль, competing effective rule. Опасное исполняется parser/mock/temp, не на рабочем объекте.

Unknown и низкая уверенность не становятся ALLOW; hard DENY сохраняется. Auditor рассматривается после реальных residual-ASK metrics. Пакет вопросов Q не становится пакетом полномочий A; последнее имеет собственный trusted approval contract.

## 8. Очищенное наблюдение и общий опыт

Согласовать с ScopedKB класс операции, версию/применимость, outcome, код причины, агрегированные метрики и безопасные evidence references. Это смысл данных, не новая глобальная schema. Не экспортировать полный shell, stdin/stdout/stderr, env, private paths, тексты задач/ответов или secrets.

Primary записи остаются в исходном scope. Common — отдельная очищенная проекция. Повтор доставки отличается от независимого случая; модельная причина помечается как inference. Ошибка записи опыта не повторяет исходное действие.

Permission-события не навязываются через agent-safe, который их не видит. Каждый источник отвечает за своё наблюдение. В базу не передаётся право изменять policy. Рекомендация и исправление проходят владельца, tests/review и installation; сырое observation не становится активной инструкцией.

## 9. Результат итерации и критерии закрытия

Отчёт содержит методику/покрытие, версии и условия, измеренные значения и unknown, полезность результата, ограничения сравнения, отрицательные проверки, какой diff внесён и что фактически установлено. Private evidence не копируется в публичный отчёт.

Разделять: proposal/PR/merged/released/installed/measured. PR открыт не означает меньше окон на ПК. Новая документация не закрывает MP-3, #39/#48, profile integration или общий stage автоматически.

Приёмка первого полезного результата: один прослеживаемый случай с доказанной причиной, ограниченным исправлением, сохранёнными safety-инвариантами, подтверждённым применением и сопоставимым пользовательским эффектом. Расписание/база/R6 могут развиваться отдельно; их отсутствие не препятствует раннему ручному разбору.
