# Отдельный владелец согласия: Linux-прототип

Дата: 08.10.2026. Связано с ssh_relay#52, opencode_permissions#46/PR #47 и agent-safe#36/PR #37.

## Принятое направление

Весь процесс OpenCode, включая загруженные плагины, находится с агентской стороны границы. Его native permission.reply не принимается внешним владельцем как доказательство согласия человека. Отдельный владелец хранит неизменяемый запрос и принимает решение через канал, недоступный агентской учётной записи.

Первый пример — установка пакета на испытательной Ubuntu. Агент предлагает конкретную команду и цель. Владелец сохраняет точную запись предложения. Подтверждение относится только к этой записи. Изменение команды, argv, executable, cwd, UUID задания/транзакции, SSH identity/поколения, policy revision или execution host меняет SHA-256 операции и требует отдельного решения. Разрешение start не разрешает stop.

Это архитектурное направление следующего прототипа, не включение допуска в рабочую установку. Код расположен в tests/opencode_2_0_23; production policy и реестр совместимости не меняются.

## Реализованная испытательная граница

`approval_owner.py` — отдельный процесс без прав root. В CI владелец работает как www-data, OpenCode как daemon, Shell-команда как nobody. Это стандартные учётные записи одноразового CI-узла; они не создаются и не изменяются. На пользовательском компьютере такой способ установки не предлагается: нужны выделенные учётные записи и отдельная процедура развёртывания.

Есть два Unix socket. Агентский допускает propose, inspect, cancel и synthetic consume; решения approve/reject через него отвергаются. Закрытый socket размещён в каталоге владельца с mode 0700, сам socket имеет mode 0600. Его клиент должен иметь UID владельца. UID берётся ядром Linux через SO_PEERCRED; поле uid в JSON не даёт полномочий.

Каталог публичного socket принадлежит владельцу и не доступен агенту для записи. Код владельца в fixture принадлежит root и не изменяется агентскими процессами. Пароля или токена решения в argv/environment агента нет. Состояние запросов хранится только в памяти отдельного владельца, а не в доступном агенту project-файле.

Операция копируется в канонические неизменяемые UTF-8 байты. Закрытый inspect возвращает владельцу эту сохранённую запись для проверки; агентский inspect возвращает состояние и digest. Право одноразово потребляется под блокировкой до ответа consume. Reject, cancel, истечение срока, закрытие владельца, неизвестный запрос и повтор не допускают потребление. После перезапуска старые request ID не восстанавливаются автоматически.

В unit-проверках есть отдельный запрет по hash команды. Он проверяет порядок обработки, но не заменяет полную production policy. Аналогично переданная SSH identity здесь — связываемые синтетические данные, а не результат настоящего подключения к SSH.

## Реальный опыт OpenCode

Upstream неизменён: anomalyco/opencode@0fd7e2829449b052abf0078666669302923d77af, OpenCode 2.0.23, Bun 1.4.2; сборка без встроенного веб-интерфейса.

`run_protected_owner_probe.py` запускает настоящий CLI в default и stdio, штатно загружает JS-плагин и использует настоящий Session.shell. Проверяемые действия ограничены созданным испытательным владельцем и его временными файлами. Другие процессы и секреты не исследуются.

Агентский плагин предлагает синтетическую операцию, затем пытается выдать решение через закрытый socket, агентский socket и JSON с подставленным UID владельца. Он также проверяет чтение/запись созданного private-файла, чтение /proc/PID/environ созданного владельца и право сигнала через kill(PID, 0), без отправки сигнала. Все эти действия должны получить отказ.

Контрольный опыт сохраняется: тот же плагин успешно отвечает once на настоящий native pending request OpenCode. Этот ответ удаляет native request, но внешний запрос должен остаться pending, а consume — вернуть APPROVAL_REQUIRED. Таким образом проверяется, что native once не переносит полномочие через внешнюю границу.

Настоящая Shell-команда под tools UID отдельно пытается предложить и подтвердить свою синтетическую операцию; предложение допускается, approve/подстановка UID/чтение private-состояния/потребление до решения должны быть отвергнуты.

Затем испытательный owner-client под UID владельца читает неизменяемую запись и проверяет отказ при изменённом digest. Отдельная консоль review требует UID владельца, закрытый socket и настоящий терминал: передача ответа через pipe отвергается. Консоль сама получает сохранённую запись от владельца, выводит её экранированным JSON (управляющие символы, ANSI и Unicode-направления не меняют показ) и спрашивает ДА; любой другой ответ означает reject.

В CI настоящий процесс консоли под UID владельца запускается в псевдотерминале. Испытательная программа проверяет, что показана сохранённая операция и её digest, затем имитирует ввод ДА. Только после этого плагин может один раз потребить синтетическое разрешение. Повтор отвергается. Код отдельной консоли реализован, но ввод в этом опыте принадлежит root fixture, а не человеку; actual_human_ui_proof остаётся false.

## Граница готовности

Прототип не запускает SSH, sudo-job, пакетный менеджер или какую-либо согласованную команду. Synthetic consume — проверка автомата, не передаваемый production grant. Он не объявляет root-operation доступной агенту.

Ещё нужны:

1. Защищённый интерфейс человека, показывающий запись самого владельца и передающий решение без агентского посредника. Настоящее действие человека проверяется отдельно.
2. Доверенное приготовление реального вызова: нельзя принимать агентские argv или объявленную SSH identity за проверенную команду/цель. Исполнитель должен связать фактически подготовленный вызов, policy и identity с рассмотренной записью.
3. Размещение root-enabled relay и его credentials с доверенной стороны. Если агент сохраняет прямой доступ к прежнему sudo-job API, он обходит новый допуск — внешний владелец этого автоматически не устраняет.
4. Подключение к durable барьеру agent-safe до start, учёт потребления до отправки, восстановление после аварии без повторной мутации и отдельный stop. Память текущего прототипа не заменяет этот журнал.
5. Полная сквозная приёмка реальной установки пакета на одноразовой Ubuntu. Windows требует собственной проверенной границы учётных записей/прав; Linux-результат на неё не переносится.

До этих шагов native_sudo_job_admission_ready=false; реестр 2.0.23 закрыт, интеграционные PR остаются черновыми. Рабочие ПК, VPS и установленный набор инструментов не меняются.

## Проверка перед CI

12 unit-проверок автомата прошли локально, включая неизменяемость записи, подмену связуемых полей, отказ агенту, параллельное потребление, повтор, cancel/reject/expiry, закрытие/перезапуск и отдельный stop. Python py_compile, node --check и проверка структуры workflow успешны. Они не являются проверкой Linux UID или реального OpenCode; эти свойства проверяются отдельным CI-опытом по опубликованному HEAD.
