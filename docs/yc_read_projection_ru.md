# YC: проверка и ограничение полей ответа о снимке

Статус: **реализованный автономный компонент подготовки данных** задачи #59.
Модуль: `tools/yc_read_projection.py`; проверки: `tests/test_yc_read_projection.py`.
Полная адресная авторизация и подключение к установленному guard ещё отсутствуют.

## Что делает компонент

`project_snapshot_context(vm_response, disk_response, snapshot_response,
selection=SnapshotSelection(...))` принимает три неизменяемые последовательности
байтов JSON и ожидаемые ID каталога, ВМ, диска и снимка. Функция не открывает
файлы, не запускает процессы, не обращается в сеть и не читает политику/ключи.
Ожидаемые ID — данные для сравнения, а не доказательство согласия владельца.

Поддерживается только явно выбранное представление `compute-rest-json/v1`:
имена полей REST API в camelCase. Это подтверждённый формат API, не утверждение
о выводе установленной версии YC CLI. Автоматическое угадывание или смешивание
camelCase/snake_case исключено. Для будущего потребителя CLI нужно отдельно
подтвердить точный формат и способ получения такого ответа.

Проверяются одновременно:

- все три ID и принадлежность ожидаемому каталогу;
- присутствие выбранного диска среди загрузочного/дополнительных дисков ВМ;
- обратная ссылка диска только на выбранную ВМ;
- ссылка снимка на исходный диск;
- совпадение размеров диска и снимка в этом узком контексте;
- типы, допустимые состояния и календарная корректность времени.

Результат содержит только заранее перечисленные поля ВМ, диска и снимка из
проекта решения A0. Имена, описания, метки, пользовательские данные, сетевые
адреса, сведения KMS и неизвестные поля исключаются. При ошибке частичный
результат не возвращается; исключение содержит только фиксированный код.
Исключение JSON-парсера с исходным документом не сохраняется как контекст ошибки.

Размеры остаются десятичными строками int64; дробное представление запрещено.
Время UTC сохраняет исходную точность до девяти знаков долей секунды.
`snapshot_ready` означает только совпадение переданных состояний disk/snapshot
с READY. Функция не доказывает подлинность ответа, свежесть наблюдения,
согласованность данных приложения или возможность восстановления.

Поэтому результат всегда содержит:

```json
{
  "authorization_granted": false,
  "independent_guard_readback": false,
  "restore_verified": false
}
```

Переданные во входных документах `trusted`, `approved` и аналогичные признаки
удаляются вместе с остальными непредусмотренными полями. Успех сравнения не
меняет ASK/DENY и не позволяет исполнителю продолжить заблокированный вызов.

## Явные ограничения узкого профиля

| Ограничение | Поведение |
|---|---|
| Ответ больше 64 КиБ, пустой ответ, не bytes | отказ до разбора |
| Глубина JSON больше 16 или более 2048 узлов | отказ |
| Повторный ключ, несколько JSON-документов, NaN/Infinity, дробное число, недопустимый Unicode | отказ |
| ID вне ASCII-профиля из 1–50 букв/цифр/`_`/`-`, первый знак не буква/цифра | отказ |
| Общий диск с несколькими подключёнными ВМ | отказ, чужие ID не выдаются |
| Повторное подключение того же диска или более 64 дополнительных дисков | отказ |
| Размер диска изменился после снимка | нужен новый контекст; это не диагноз неисправности снимка |
| Время с часовым смещением вместо UTC Z либо более девяти знаков долей секунды | отказ этого профиля |
| Неизвестное состояние или недостаток обязательных полей | отказ |

Ограничение 64 КиБ относится к уже переданному документу. Оно не ограничивает
объём вывода запущенного процесса: будущий потребитель обязан ограничить захват
stdout/stderr и время исполнения **до** накопления ответа, исключить прямой
вывод в терминал модели и сохранять только проверенный результат.

## Место в дальнейшем подключении

Этот модуль пока не входит в content-bound артефакт: действующий dispatcher
не имеет доверенного источника адресного разрешения и не перехватывает вывод.
Добавлять неиспользуемый модуль в выпуск и обновлять установленную машину ради
этого было бы неверным подтверждением готовности.

Правильная последовательность будущего потребителя:

1. Доверенный владелец разрешения получает выбранную цель и согласие владельца
   на чтение точных ID, связывает их со свежим контекстом и сроком.
2. Канонический permission layer проверяет точную операцию и жёсткие запреты.
3. Только после допуска исполнитель ограниченно получает ответы; сырой вывод
   не отправляется модели. Несоответствие, отказ или unknown не запускают повтор.
4. Компонент проверяет поля и выдаёт фиксированный набор данных. Свидетельство
   происхождения и свежести формирует доверенный потребитель отдельно; нельзя
   просто заменить false на true по аргументу агента.
5. После сквозных имитационных проверок выпускаются новый артефакт, проверенная
   привязка версии в `agent-toolchain` и управляемое обновление с проверкой на машине.

В текущем `main` нет рабочего Windows-интерфейса владельца разовых разрешений.
Библиотечные HostPort/ExecutionPort в PR #37 и опыт Linux-владельца в PR #47
не являются установленным Windows-транспортом. Прямой перенос JSON-флага или
вызов скрытого `yc.exe` этот пробел не закрывает. Новые чтения остаются ASK_USER;
создание/удаление снимка, новая ВМ и восстановление не становятся разрешёнными.

## Основания и проверка

Официальные описания полей:

- [Instance.Get](https://yandex.cloud/en/docs/compute/api-ref/Instance/get).
- [Disk.Get](https://yandex.cloud/en/docs/compute/api-ref/Disk/get).
- [Snapshot.Get](https://yandex.cloud/en/docs/compute/api-ref/Snapshot/get).

Тесты используют только синтетические ID и закрываемые маркеры данных. Они
проверяют направление связей, точный состав результата, большие числа,
наносекунды, неверные документы, пределы разбора, отсутствие утечки через
результат/ошибки, поддельные признаки согласия и сохранение ASK у classifier.
Доступ в облако и восстановление этими тестами не подтверждаются.
