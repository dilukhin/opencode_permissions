# Пакетное согласование через единственного владельца разрешений

Статус: **A0 / проект для рассмотрения**. Требования к реализации и испытаниям, не действующий формат API и не новый источник полномочий.
Связано с [#48](https://github.com/dilukhin/opencode_permissions/issues/48), [#46](https://github.com/dilukhin/opencode_permissions/issues/46), [PR #47](https://github.com/dilukhin/opencode_permissions/pull/47).
Общие границы: [контракт интеграции](cross_project_integration_contract_v1_ru.md), [модель угроз](default_threat_model_ru.md), [пакетные вопросы](batch_interaction_design_ru.md).

## 1. Что переиспользуем

Основа — существующий испытательный владелец согласия из PR #47, а не новый посредник. Его [описание](https://github.com/dilukhin/opencode_permissions/blob/agent/sudo-job-policy-46/docs/sudo_job_protected_owner_ru.md) и [код](https://github.com/dilukhin/opencode_permissions/blob/agent/sudo-job-policy-46/tests/opencode_2_0_23/approval_owner.py) пока находятся в отдельной ветке. Эти ссылки обозначают кандидата на интеграцию, не наличие реализации в main.

| Свойство | Уже проверено в прототипе | Чего это не доказывает |
|---|---|---|
| Источник решения | Разные Linux UID, закрытый канал, SO_PEERCRED; агентский процесс и проверенный плагин не принимают решение | Личность физически действующего человека; защиту от администратора |
| Привязка | Неизменяемая копия операции, SHA-256, проверка изменённых полей | Достоверность объявленной агентом SSH-цели или фактического argv |
| Однократность | Атомарное потребление в памяти, отказ при повторе, отмене и истечении срока | Устойчивое потребление совместно с реальным исполнением после аварии |
| Консоль | Показывает запись владельца, экранирует управляющие символы, отвергает pipe | Ввод человеком: CI вводил ответ испытательной программой через PTY |
| Исполнение | Только synthetic consume | Запуск SSH/root-команды, закрытие прежних прямых каналов |
| Пакет | Ещё не реализован | Одновременное решение по нескольким операциям |

Версию, платформу и HEAD каждого нового опыта фиксировать в отдельном отчёте. Linux-результат не переносится на Windows или другую версию OpenCode.

Прототип задаёт усиленную границу: весь OpenCode с плагинами находится с недоверенной стороны. Это обоснованный кандидат для защищённого допуска рискованных действий; он не делает отдельные UID и новый сервис обязательными для каждого безопасного чтения в обычной модели угроз.

## 2. Какие действия включать

Пакет состоит из конечного перечня **точных подготовленных операций** с остаточным ASK_USER. Первая реализация не выдаёт разрешений на будущие произвольные команды или семейства wildcard.

- Автоматически допустимые действия выполняются через существующую политику без согласования.
- Hard DENY не включается в список подтверждаемых операций и не отменяется решением пользователя.
- Неразобранная операция возвращается на уточнение/декомпозицию; неизвестность не превращается в исполняемый допуск.
- Ответы Q, текст плана, native once/always и --approved не являются источником защищённого согласия.
- Повторяемые полномочия по узким шаблонам отложены до отдельного доказательства необходимости и ширины разрешений.

Доверенная часть должна приготовить и проверить фактический вызов. Данные предложения агента могут быть входом, но не доказательством цели, идентичности исполняемого файла или разрешённости операции.

## 3. Неизменяемый перечень

Владелец сохраняет снимок пакета до показа пользователю. Логические поля, пока без новой схемы обмена:

- идентификатор пакета, экземпляр владельца и идентичность вызывающего контекста;
- версия правил и исследуемого профиля;
- стабильный идентификатор каждого элемента и точная идентичность операции;
- цель, среда, последствия, риск, обратимость и причина остаточного ASK_USER;
- зависимости между элементами, условия продолжения и срок действия;
- ожидаемая проверка результата; остановка и восстановление не подразумеваются разрешением start.

Идентичность операции следует существующему NormalizedOperation/AuthorizationGrant и подтверждённому PreparedProcess. Для удалённого действия она включает проверенную SSH-цель/поколение соединения; для фактического запуска — executable/argv/cwd и доказанные зависимости. Caller-controlled поля сами по себе не становятся trusted facts.

Канонический digest перечня связывает идентификаторы, порядок, точные операции, зависимости и границы срока/применения. Алгоритм и формат выбираются после проверки существующего владельца, без второго несовместимого механизма canonicalization. Повторные идентификаторы/непредусмотренные дубликаты, неизвестные поля и неоднозначное представление отвергаются.

Добавление, удаление, перестановка или изменение элемента создаёт новую ревизию перечня. Старое решение нельзя молча перенести на обновлённый пакет. Изменившееся действие требует нового согласования; уже потреблённые допуска не восстанавливаются.

## 4. Один просмотр, отдельные решения

Доверенный интерфейс получает сохранённый перечень непосредственно от владельца. Показывает понятное назначение и последствия каждого действия, точные технические данные доступны для проверки. Управляющие символы экранируются; секреты в перечень и публичный журнал не помещаются.

Пользователь за один просмотр выбирает для каждого элемента подтвердить, отклонить либо отложить. Не выбранный элемент не получает допуска. Выбор и итоговый состав видны до отправки; возможен отказ от всего пакета. Это один этап общения, а не обязательное безусловное «ДА всему».

Решение связано с digest перечня и полным соответствием item ID → decision. Владелец проверяет доверенный канал, актуальный экземпляр, версию перечня, срок и допустимость решения. Пропуск/дубликат/чужой ID, устаревшая ревизия или изменённый digest отвергают запись решения целиком; незавершённый ответ не создаёт часть разрешений.

Запись полного решения должна иметь однозначный результат в защищённом состоянии. При потере ответа интерфейс сначала читает состояние этого решения; не создаёт новый пакет и не повторяет мутации. Таймаут не трактуется как согласие.

Полномочный процесс владельца и физическое действие пользователя — разные свойства. Ручная приёмка может подтвердить конкретный сеанс ввода пользователем в заданной модели угроз. Она не доказывает, что любой будущий ввод обязательно сделан человеком. Криптографическое подтверждение на отдельном устройстве — отдельное усиленное требование; оно не считается реализованным или автоматически обязательным.

## 5. Индивидуальное исполнение и учёт

Один просмотр выдаёт отдельные точные одноразовые допуска; он не запускает пакет и не заменяет проверку каждого действия:

1. Проверить наличие собственного подтверждённого элемента и совпадение фактической операции.
2. Повторно проверить hard DENY, версию правил/профиля, срок, контекст и зависимости.
3. Передать действие в agent-safe для его проверки состояния и безопасного исполнения.
4. Связать устойчивое однократное потребление с журналом допуска **до отправки изменения**. Протокол совместной записи/возобновления должен исключать запуск без записанного потребления и выдачу второго допуска после аварии.
5. Проверить результат через agent-safe; транспорт предоставляет фактическое состояние и идентичность задания.

Память Ledger из PR #47 этому критерию пока не соответствует. Журнал результата, проверка и восстановление остаются у agent-safe; владелец согласия не становится вторым исполнителем.

После потребления допуск не переиздаётся автоматически, даже если операция завершилась неуспешно. Новый запуск/stop/recovery требует собственного решения согласно политике; безопасный status может выполняться автоматически, если это доказано.

Пакет не является транзакцией изменений: завершённые операции не откатываются из-за отказа следующей. Отклонённый/отложенный элемент и его зависимые действия не исполняются. Независимые согласованные и безопасные пути могут продолжаться, когда это подтверждено зависимостями и состоянием.

При drift затронутый допуск теряет силу; изменение общей policy/context блокирует весь зависящий от него scope. При неизвестном результате остановить зависимую цепочку и выполнить разрешённую диагностику, без слепого повторного запуска. Отмена предотвращает ещё не начатые действия; уже выполняемое действие требует отдельного stop. После перезапуска старые допуска закрыты, пока не доказан безопасный протокол восстановления.

## 6. Проверяемый корпус A0

Все случаи сначала parser-only/mock или synthetic temp fixture, без реальных SSH/root-команд.

| ID | Вход/сбой | Обязательный результат |
|---|---|---|
| B01 | Два подтверждения, один отказ | Отдельные допуска только первым двум; отказ и его зависимые пути закрыты |
| B02 | Ответ question «Да», native once/always, --approved | Состояние внешнего владельца не меняется |
| B03 | Агент/child/plugin отвечает через любой доступный канал | Не может записать защищённое решение; поле UID в JSON не помогает |
| B04 | Подмена перечня/порядка/item ID/digest/зависимостей | Старое решение не применяется; частичной выдачи при ошибке записи нет |
| B05 | Подмена actual argv/цели/host identity/policy/context | Несовпадение блокирует действие до запуска |
| B06 | DENY, unknown или nested opaque внутри предложения | Никакого исполняемого допуска этому элементу |
| B07 | Истечение срока/отмена/перезапуск/чужой вызывающий контекст | Допуск закрыт; таймаут не согласие |
| B08 | Два конкурирующих consume одного элемента | Не более одного успешного потребления |
| B09 | Потеря ответа после решения/потребления/отправки start | Read-only сверка устойчивого состояния; повторная мутация не происходит |
| B10 | Отказ зависимого элемента или unknown результата | Останавливается зависимая цепочка; независимость не предполагается |
| B11 | Разрешён start, предлагаются stop/recovery | Исходный допуск не разрешает новые действия |
| B12 | Остался прямой root-enabled relay/API/credential | Интеграционная приёмка отвергается: наличие владельца обход не закрывает |
| B13 | ANSI/control/bidi или secret-like поля в показе | Безопасный показ либо отказ; публичный отчёт без секретов |
| B14 | Испытательный наблюдатель теряет события/корреляцию | INCONCLUSIVE; намеренно внедрённый дефект обязан давать FAIL |

## 7. Условия дальнейшей работы и локальная часть

A0 готов к рассмотрению после сопоставления с PR #47, AuthorizationGrant и владельцами смежных компонентов; это не закрывает A1. Перед A1 нужны фактический MP-3 baseline, exact version/platform proof, выбранная измеренно полезная семья ASK и отдельное принятие реализации. Прохождение Q1 не выдаёт технических разрешений и может идти независимо после принятия Q0.

Сначала Web/CI: проверить отдельное согласие, закрыть фактическую подготовку вызова, прямые обходы и устойчивый барьер исполнения вместе с существующими владельцами. Только после этих критериев проверять пакетирование допусков. Нельзя объявить рабочую безопасность пакета по тестам одного in-memory Ledger.

Локальный агент потребуется для сбора фактического профиля установки и наблюдения интерфейса; сам пользователь выполняет ввод решения. Отдельная ручная проверка консоли допустима раньше полного допуска к исполнению, но остаётся синтетической и не закрывает A1.

Будущее ограниченное задание должно фиксировать exact workspace/HEAD, одноразовую Linux-среду, проверенную версию и способ разделения учётных записей, разрешённые временные пути, сценарии approve/reject/отсутствие ответа, идентичность показанной и сохранённой операции, ожидаемый отчёт и условия остановки. Агент не вводит ответ за пользователя, не создаёт канал самоодобрения и не меняет рабочие ПК/VPS. Если изоляция или профиль отсутствуют, вернуть факты и остановить проверку; не устанавливать новую границу импровизацией.

Пока создание такого задания на реальное исполнение преждевременно: зависимые интеграционные проверки не завершены. Текущая документационная итерация не требует локального агента.
