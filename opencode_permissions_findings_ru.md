# OpenCode Permissions — исходные findings и вопросы для исследования

Дата среза: 2026-08-07
Статус: handoff / research notes
Нормативность: не является спецификацией; всё изменяемое поведение OpenCode перепроверять

## 1. Подтверждённые факты по актуальной документации OpenCode

На дату среза официальная документация подтверждает:

- permissions возвращают `allow`, `ask` или `deny`;
- `--auto` автоматически подтверждает только то, что иначе было бы `ask`; явный `deny` сохраняется;
- для гранулярных правил используется pattern matching;
- при нескольких совпадениях последнее совпавшее правило побеждает;
- `*` и `?` являются простыми wildcard;
- `external_directory` срабатывает на путь вне рабочего дерева;
- большинство permissions по умолчанию permissive, но `external_directory` и `doom_loop` по умолчанию `ask`;
- чтение `.env` по умолчанию ограничено;
- permission можно перекрывать на уровне агента;
- `task` контролирует запуск субагентов;
- custom tools размещаются в `.opencode/tools/` или глобальном каталоге;
- custom tool может использовать имя встроенного и тем самым получить приоритет над встроенным tool;
- документация прямо приводит замену встроенного `bash` пользовательским ограниченным wrapper как допустимый механизм.

Это делает технически возможным собственный command gate без модификации ядра OpenCode.

## 2. Подтверждённые факты по `agent-safe`

Текущий `agent-safe` использует короткий `AGENTS.md` с основным правилом:

- любое изменение внешнего состояния считается рискованным;
- неизвестную подсистему сначала исследуют read-only;
- перед опасным действием определяются target, environment, expected state и rollback;
- выполняется одно атомарное действие;
- после unexpected result включается Recovery Mode.

Bootstrap `safe opencode-bootstrap`:

- умеет global и project scope;
- имеет `--dry-run` и `--apply`;
- делает backup;
- обновляет `opencode.json`;
- копирует skills;
- добавляет короткий блок в `AGENTS.md`;
- записывает операцию в журнал.

Текущий шаблон `opencode.json` в `agent-safe` консервативен:

- общий `*` -> `ask`;
- read -> allow с deny для секретоподобных файлов;
- safe read-only Git -> allow;
- `safe *` -> allow;
- разрушительные команды -> deny;
- `edit`, `external_directory`, `doom_loop` -> ask.

Главный урок: безопасность реализуется не одним промптом, а комбинацией слоёв.

## 3. Исходная проблема проекта

Практически наблюдается слишком большое количество permission prompts.

Проблема двойная:

1. безопасные повторяющиеся действия требуют человека;
2. когда вопрос действительно важен, UI показывает длинную shell-команду, которую трудно оценить.

После серии запросов пользователь начинает подтверждать их почти автоматически. Поэтому частые prompts не обязательно повышают безопасность.

## 4. Рабочая гипотеза

Более эффективная модель:

```text
deterministic allow
+ deterministic deny
+ parser/effect analysis
+ optional model auditor
+ rare human approval
```

Пользователь должен быть последним уровнем, а не ручным shell parser.

## 5. Почему одной модели недостаточно

Модель-аудитор может ошибиться или пропустить скрытый эффект.

Поэтому:

- hard deny должен срабатывать до модели;
- model auditor должен работать только в серой зоне;
- низкая уверенность -> пользователь;
- модель не должна иметь инструментов выполнения;
- предпочтителен короткий структурированный вход;
- ответ должен быть машинно проверяемым.

## 6. Почему одного command-prefix parser недостаточно

Опасность может быть спрятана в:

```text
git status && rm ...
find ... -exec ...
find ... | xargs rm
python -c ...
powershell -Command ...
cmd /c ...
bash -c ...
ssh_relay ... "<remote payload>"
```

Нужно анализировать всю структуру действия.

## 7. Особый риск `find`

Нельзя разрешать `find *` только потому, что обычно он используется для поиска.

Минимально опасные примитивы:

```text
-delete
-exec
-execdir
-ok
-okdir
```

Отдельный риск — передача результата в destructive downstream через pipeline.

Для обычного поиска лучше встроенный `glob`.

## 8. Особый риск `ssh_relay`

Локальный permission на `ssh_relay` ничего не говорит о безопасности удалённой команды.

Нужно выяснить, возможно ли:

- получить remote payload до исполнения;
- разобрать его тем же parser;
- ограничить session/host;
- ограничить remote cwd;
- разрешать фиксированные операции;
- интегрировать с `agent-safe ssh-relay-*`.

Возможно, remote layer станет главным местом повторного использования agent-safe.

## 9. UX подтверждения

При `ASK_USER` надо показывать семантику:

```text
Цель
Фактические действия
Локальная/удалённая среда
Затрагиваемые объекты
Изменения
Риск
Обратимость
Причина запроса
Рекомендация
```

Сырая команда — вторичный раскрываемый блок.

Если система не может достоверно объяснить команду, безопаснее разбить её на атомарные операции.

Этап 0 должен установить:

1. точную версию OpenCode;
2. способ установки и обновления;
3. активную оболочку на Windows;
4. путь всех global/project config;
5. наличие agent config;
6. фактический порядок merge;
7. что именно OpenCode считает parsed bash command;
8. как permission matcher ведёт себя с `&&`, `||`, `;`, pipelines;
9. какие approval patterns предлагает `always`;
10. как ведёт себя `external_directory`, если OpenCode запущен из общего родителя двух Git-репозиториев;
11. можно ли перехватить/заменить `bash` без потери встроенных возможностей;
12. какие plugin hooks доступны до/после tool execution;
13. можно ли custom tool безопасно вызвать отдельную модель;
14. можно ли использовать subagent как auditor без права исполнения;
15. можно ли программно сформировать собственный человекочитаемый approval prompt.

## 11. Вопрос по model auditor

Нужно сравнить минимум три реализации.

### Вариант A — subagent OpenCode

Плюсы:

- встроенная инфраструктура;
- отдельные permissions;
- быстрое прототипирование.

Минусы:

- неясно, можно ли сделать вызов обязательным на уровне tool gate;
- возможна зависимость от решения основной модели вызвать subagent.

### Вариант B — отдельная модель из custom tool/plugin

Плюсы:

- обязательный вызов для серой зоны;
- структурированный контракт;
- основная модель не может его пропустить.

Минусы:

- потребуется API/SDK;
- стоимость и задержка;
- обработка отказов модели.

### Вариант C — model-free parser

Плюсы:

- детерминированность;
- низкая стоимость;
- предсказуемый аудит.

Минусы:

- трудно понять нестандартные CLI;
- быстро растёт сложность правил.

Наиболее вероятен гибрид B/C.

## 12. Вопрос по approval UI

Штатный `ask` OpenCode может не позволять заменить отображение сырой команды собственным summary.

Если это подтвердится, возможны направления:

- custom tool сам вызывает `question` с подготовленным описанием;
- plugin перехватывает событие и показывает собственное представление;
- custom tool возвращает structured `ASK` и основной агент вызывает question;
- отдельный локальный approval service/UI.

Нужно выбрать механизм, где проверка не зависит только от добровольной дисциплины основной модели.

## 13. Секреты

При проектировании trusted read нельзя расширить доступ к секретам случайно.

Нужно проверить:

- дефолтные deny `.env`;
- дополнительные расширения `.key`, `.pem`, `.p12`, `.pfx`;
- project-specific secret files;
- вывод переменных окружения;
- command logs;
- remote logs.

Модель-аудитор не должна получать реальные секреты.

## 14. Тестовая стратегия

Нужен корпус permission cases.

Классы:

```text
safe_read
safe_git_read
safe_build
safe_test
file_write
file_delete
git_destructive
system_service
secret_read
nested_shell
interpreter
remote_safe
remote_destructive
unknown_cli
purpose_mismatch
```

Каждый case должен иметь:

```text
input
purpose
environment
expected_decision
expected_effects
expected_user_summary
```

Отрицательные кейсы выполняются только в mock/parser-only режиме.

## 15. Метрики пилота

Собирать:

```text
permission_prompt_count
human_approval_count
auto_allow_count
hard_deny_count
auditor_count
auditor_latency
false_block_count
unsafe_test_allow_count
raw_command_open_count
```

Главная метрика — не просто меньше prompts, а меньше бессмысленных prompts при сохранении нулевого числа опасных автоматических разрешений на тестовом корпусе.

## 16. Рабочая среда первого пилота

OpenCode запускается из:

```text
C:\Users\d.ilyhin\Projects\bsdownloader
```

Вложенные репозитории:

```text
C:\Users\d.ilyhin\Projects\bsdownloader\bsdownloader
C:\Users\d.ilyhin\Projects\bsdownloader\bsdownloadgui
```

Нужно проверить, устраняет ли это ненужные `external_directory` prompts между репозиториями.

Удалённый макет используется через:

```text
ssh_relay
session: default
```

## 17. Что пока не решено

Не считать принятыми решениями:

- замену встроенного `bash`;
- обязательное использование модели;
- конкретную малую модель;
- отдельный репозиторий runtime-компонента;
- интеграцию в `agent-safe`;
- формат permission DSL;
- формат AST shell-команды;
- собственный approval UI.

Сначала требуется read-only аудит и прототип.
