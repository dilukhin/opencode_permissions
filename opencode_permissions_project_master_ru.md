# Управляющий документ проекта OpenCode Permissions

Версия: 0.1
Дата: 2026-08-07
Статус: начальный управляющий документ
Область: OpenCode permissions, custom tools/plugins, автоматическая классификация команд, запросы подтверждения пользователю
Архитектурный образец: `agent-safe`

## 1. Назначение проекта

Цель проекта — разработать практический режим работы OpenCode, который сочетает высокую автономность агента с технически контролируемыми границами опасных действий.

Проблема возникла из реального рабочего процесса: OpenCode регулярно запрашивает подтверждение на безопасные и повторяющиеся действия, а пользователю приходится читать длинные сгенерированные команды. Это замедляет разработку и постепенно снижает качество ручного контроля: после серии однотипных запросов пользователь начинает подтверждать их почти автоматически.

Поэтому задача не сводится к «разрешить больше команд». Требуется изменить саму модель принятия решения:

```text
простое и безопасное действие
    -> разрешить автоматически

явно опасное действие
    -> заблокировать технически

неоднозначное действие
    -> разобрать и оценить автоматически

остаточная неопределённость
    -> спросить пользователя понятным языком
```

## 2. Главные требования

### 2.1. Автономность

Штатная работа агента не должна останавливаться на:

- чтении файлов;
- поиске;
- `grep`/`glob`/безопасном `git grep`;
- просмотре Git;
- сборке;
- CTest/pytest/unit tests;
- повторном запуске теста;
- обычной read-only диагностике;
- формировании журналов;
- безопасных операциях в заранее известных временных каталогах.

Целевое число запросов пользователю для обычного пакетного цикла:

```text
0
```

Допустимо одно подтверждение на начало ограниченной удалённой операции, если более точная техническая граница пока не реализована.

### 2.2. Сохранение защитных границ

Автономность не должна означать безусловный shell-доступ.

Опасные операции должны оставаться `deny` или требовать отдельного явно контролируемого протокола. Примеры:

- разрушительные Git-команды;
- произвольное удаление;
- `sudo`;
- управление системными службами;
- production deployment;
- изменение MongoDB;
- изменение секретов;
- неизвестные удалённые операции;
- запись в production-каталоги;
- операции с большим или неясным радиусом воздействия.

### 2.3. Осмысленное подтверждение

Если пользователь привлекается, система должна спрашивать не:

```text
Разрешить <длинная строка shell>?
```

а:

```text
Что агент хочет сделать?
Где?
Что изменится?
Какой риск?
Можно ли отменить?
Почему требуется человек?
```

Сырая команда остаётся доступной для аудита.

## 3. Источники истины и приоритет

### 3.1. Поведение OpenCode

Для синтаксиса и семантики permissions главным источником является:

1. фактическая установленная версия OpenCode;
2. официальная документация этой версии;
3. только затем накопленные findings.

OpenCode быстро развивается. Настройки из старых статей, памяти агента или старого проекта нельзя переносить без проверки.

### 3.2. Архитектурный образец `agent-safe`

`agent-safe` используется не как готовое решение этой задачи, а как проверенный образец разделения слоёв безопасности.

Из него переносится принцип:

```text
короткие правила агенту
+ техническая конфигурация
+ процедуры по требованию
+ runtime-предохранитель
+ журнал и recovery
```

Текущий `agent-safe` использует протокол:

```text
classify
-> inspect
-> expected_state
-> checkpoint
-> execute one atomic action
-> verify
-> continue/recovery
```

Для OpenCode Permissions часть этого подхода может быть упрощена для read-only и низкорисковых операций, но принципы точной цели, атомарности, верификации и Recovery Mode важны для опасных изменений.

## 4. Подтверждённые возможности OpenCode, на которых строится проект

По актуальной официальной документации OpenCode:

- разрешение имеет три результата: `allow`, `ask`, `deny`;
- существуют гранулярные правила для `bash`, `read`, `edit`, `glob`, `grep` и других инструментов;
- при нескольких совпадениях побеждает последнее правило;
- `external_directory` отдельно контролирует доступ вне рабочего дерева;
- agent-specific permissions могут перекрывать общие;
- `task` позволяет контролировать запуск субагентов;
- `--auto` автоматически подтверждает то, что осталось `ask`, но явный `deny` продолжает действовать;
- custom tools могут находиться в `.opencode/tools/` или глобальном каталоге;
- пользовательский tool с именем встроенного инструмента может заменить встроенный, в том числе `bash`.

Эти возможности делают реалистичной архитектуру, где большая часть низкорисковых действий разрешается штатной конфигурацией, а сложные shell/remote операции проходят через собственный контролируемый инструмент.

## 5. Архитектурная гипотеза

Предпочтительное направление:

```text
Основной агент
    |
    v
OpenCode permission layer
    |
    +-- очевидный ALLOW
    |
    +-- очевидный DENY
    |
    v
контролируемый command tool
    |
    +-- синтаксический разбор
    +-- определение эффектов
    +-- проверка путей/окружения
    +-- проверка локальная/remote
    |
    +-- однозначно безопасно -> ALLOW
    +-- однозначно запрещено -> DENY
    +-- неоднозначно -> auditor
                           |
                           +-- достаточно уверенно -> ALLOW/ASK
                           +-- неясно -> ASK_USER
```

Критический принцип:

```text
модель-аудитор не имеет права отменять детерминированный DENY
```

## 6. Слои решения

### 6.1. Слой A — штатный `opencode.json`

Используется для простых правил:

- `read`;
- `glob`;
- `grep`;
- LSP;
- безопасные команды Git;
- известные тестовые команды;
- явные запреты на очевидно разрушительные операции;
- ограничения внешних каталогов.

Не использовать широкие шаблоны, которые фактически превращают оболочку в универсальный обход.

Например, разрешение `python *` требует отдельной оценки, потому что `python -c` способен выполнить произвольное системное действие.

### 6.2. Слой B — парсер и классификатор команды

Нужен для команд, которые нельзя надёжно классифицировать префиксом.

Он должен видеть минимум:

- исполняемый файл;
- аргументы;
- составные операторы;
- конвейеры;
- перенаправления;
- вложенные оболочки;
- рабочий каталог;
- затрагиваемые пути;
- удалённую часть команды;
- операции чтения/записи/удаления;
- Git-эффекты;
- системные и сетевые действия.

Парсер должен быть консервативным: неизвестная конструкция не переводится в автоматический `ALLOW`.

### 6.3. Слой C — специализированные безопасные инструменты

Вместо универсального shell предпочтительны специализированные операции:

```text
safe_search
safe_git
safe_build
safe_test
safe_remote
```

Названия предварительные.

Их преимущество: интерфейс операции описывает намерение и параметры лучше, чем произвольная строка shell.

### 6.4. Слой D — модель-аудитор

Модель полезна для серой зоны:

- сложная команда;
- нестандартный инструмент;
- оценка соответствия цели фактическим действиям;
- краткое объяснение пользователю;
- предложение менее рискованного варианта.

Модель должна получать структурированные данные, а не только сырую строку.

Минимальный вход:

```json
{
  "purpose": "найти временные файлы",
  "environment": "local_windows",
  "working_directory": "...",
  "executable": "find",
  "arguments": ["...", "-delete"],
  "effects": ["file_delete"],
  "targets": ["..."],
  "hard_rules": ["..."]
}
```

Минимальный выход:

```json
{
  "decision": "ask_user",
  "risk": "destructive",
  "confidence": 0.95,
  "reason": "Команда не только ищет файлы, но и удаляет найденные объекты."
}
```

Формат и конкретная модель определяются после исследования.

### 6.5. Слой E — пользователь

Пользователь является последним уровнем, а не универсальным классификатором shell-команд.

Вопрос должен быть коротким и предметным.

## 7. Отдельные сложные случаи

### 7.1. `find`

Простой поиск:

```text
find src -type f -name "*.cpp" -print
```

не должен требовать человека после подтверждения корректности парсера.

Но нужно отличать:

```text
-delete
-exec
-execdir
-ok
-okdir
```

Также анализировать downstream:

```text
find ... | xargs rm
```

Для большинства задач предпочтительнее встроенный `glob`.

### 7.2. `ssh_relay`

`ssh_relay` нельзя считать безопасным только по локальному исполняемому файлу.

Нужно классифицировать:

1. локальный вызов relay;
2. выбранную сессию/узел;
3. удалённую команду;
4. удалённый рабочий каталог;
5. эффекты на удалённой машине.

Предпочтительное направление — ограниченный remote tool, который умеет фиксированный набор операций или повторно прогоняет удалённую команду через тот же классификатор.

### 7.3. Интерпретаторы

Отдельно учитывать:

- `python -c`;
- PowerShell `-Command`;
- `cmd /c`;
- `bash -c`;
- скрипты, которые могут быть изменены перед запуском.

Нельзя считать безопасным интерпретатор целиком только потому, что часто он используется для тестов.

### 7.4. Составные команды

Анализировать:

```text
&&
||
;
|
>
>>
```

Безопасный первый сегмент не делает безопасной всю строку.

### 7.5. Секреты

Разрешение `read` должно иметь явные исключения для чувствительных файлов.

Нужно проверять как минимум:

- `.env`;
- ключи/сертификаты;
- файлы токенов;
- локальные secret stores;
- конфигурации с credentials.

## 8. Требования к пользовательскому запросу

### 8.1. Основной экран

Пользователь должен увидеть:

```text
Цель
Действия
Среда
Затрагиваемые объекты
Что изменится
Основной риск
Обратимость
Причина запроса
Рекомендация
```

### 8.2. Подробности

Отдельно раскрываются:

- точная команда;
- разобранная структура;
- сработавшие правила;
- вывод аудитора;
- неизвестные эффекты.

### 8.3. Сравнение цели и действия

Система должна получать от основного агента краткое намерение и сравнивать его с командой.

Пример:

```text
Цель: найти файлы.
Фактический эффект: поиск + удаление.
Решение: не разрешать автоматически.
```

Расхождение цели и эффекта повышает уровень риска.

## 9. Recovery Mode

После unexpected result опасная цепочка не должна продолжаться автоматически.

Для высокорискового изменения:

1. остановить исходный путь;
2. сохранить evidence;
3. разрешить read-only диагностику;
4. построить recovery plan;
5. не выполнять cleanup/reset/force автоматически.

Это заимствуется из `agent-safe`.

Для обычного падения теста или компиляции Recovery Mode не требуется: агент должен самостоятельно исправлять такие ошибки.

## 10. Первый пилот

Первый практический пилот выполняется на рабочем дереве:

```text
C:\Users\d.ilyhin\Projects\bsdownloader
```

Внутри:

```text
C:\Users\d.ilyhin\Projects\bsdownloader\bsdownloader
C:\Users\d.ilyhin\Projects\bsdownloader\bsdownloadgui
```

Удалённый макет:

```text
ssh_relay
session: default
```

Пилот должен отражать реальную пакетную разработку:

```text
поиск
-> чтение
-> изменение кода
-> локальные тесты
-> git diff/status
-> commit/push
-> remote pull
-> сборка
-> CTest
-> сбор артефактов
```

При этом production operations остаются за границей пилота.

## 11. План работ

### Этап 0. Инвентаризация

Ничего не менять.

Собрать:

- версию OpenCode;
- способ установки;
- активную оболочку;
- все применимые конфигурации;
- `AGENTS.md`;
- agents;
- skills;
- custom tools/plugins;
- переменные `OPENCODE_*`;
- фактический рабочий каталог;
- список типичных запросов подтверждения.

Результат: baseline.

### Этап 1. Карта подтверждений

Для реальной задачи собрать:

```text
операция
tool
сырой input
какое permission сработало
что показано пользователю
решение пользователя
была ли операция фактически безопасной
```

Цель — устранить причины, а не просто включить `--auto`.

### Этап 2. Минимальная конфигурация

На основе baseline:

- разрешить встроенные read/glob/grep/LSP;
- настроить точные Git/read-only правила;
- сузить trusted roots;
- добавить hard deny;
- оставить сложный shell в `ask`.

Сначала `dry-run`/diff, затем применение с backup.

### Этап 3. Прототип классификатора

Режим без исполнения.

Вход: команды из реальных запросов.

Выход:

```text
ALLOW
DENY
ASK
+ объяснение эффектов
```

Обязательные атакующие примеры:

```text
find . -delete
find . -exec ...
git status && destructive
python -c ...
powershell -Command ...
cmd /c ...
ssh_relay ... "sudo ..."
```

### Этап 4. Custom tool / plugin

Исследовать два варианта:

1. новый специализированный tool;
2. контролируемая замена встроенного `bash`.

Не выбирать замену `bash` до проверки полного поведения и обходных путей.

### Этап 5. Модель-аудитор

Добавлять только после работоспособного детерминированного слоя.

Исследовать:

- отдельный subagent;
- отдельную малую модель;
- вызов через SDK/plugin;
- стоимость;
- задержку;
- структурированный вывод;
- поведение на атакующих примерах.

### Этап 6. Человекочитаемый approval UX

Сделать прототип описания операции.

Критерий: пользователь принимает решение без необходимости читать сырую команду.

### Этап 7. Интеграционные проверки

Положительные:

- чтение;
- поиск;
- git status/diff;
- сборка;
- тесты;
- соседний репозиторий;
- разрешённая remote build-команда.

Отрицательные — только в безопасном стенде/mock:

- delete;
- hard reset;
- clean;
- sudo;
- systemctl;
- production path;
- secrets;
- destructive remote payload.

### Этап 8. Пилот в BS Downloader

Выполнить один реальный пакет разработки.

Собрать метрики:

- число permission prompts;
- число запросов пользователю;
- число ложных блокировок;
- число автоматически разрешённых операций;
- задержка аудитора;
- ошибки классификации;
- случаи, где пользователь запросил raw command.

### Этап 9. Решение о распространении

После пилота определить:

- что оставить глобальным;
- что проектным;
- что передать в `agent-safe`;
- нужен ли отдельный новый репозиторий;
- нужна ли интеграция с `safe`;
- какие правила готовы для других проектов.

## 12. Критерии приёмки первой версии

Первая версия считается успешной, если:

1. штатный цикл поиска/сборки/тестов не требует ручных разрешений;
2. `find -delete` не проходит как обычный поиск;
3. `ssh_relay` оценивается по удалённому payload;
4. составные команды анализируются целиком;
5. hard deny нельзя отменить моделью-аудитором;
6. секретные файлы не открываются автоматически;
7. пользователь получает объяснение вместо одной сырой команды;
8. отрицательные проверки не требуют разрушения реальных данных;
9. конфигурация имеет backup и понятный rollback;
10. после перезапуска OpenCode поведение воспроизводится.

Целевые показатели пилота:

```text
обычная пакетная задача: 0 пользовательских подтверждений
архитектурно неоднозначное действие: <= 1 осмысленного вопроса
ложные автоматические разрешения опасных тестовых случаев: 0
```

## 14. Правила изменения конфигурации

Любая настройка OpenCode выполняется как изменение инфраструктуры:

1. backup;
2. diff;
3. применение;
4. перезапуск сессии при необходимости;
5. положительная проверка;
6. отрицательная проверка;
7. фиксация фактического поведения;
8. rollback при неожиданном результате.

Нельзя объявлять правило безопасным только потому, что конфигурация выглядит правильно.

## 15. Документация и границы знаний

Документы делятся на:

- управляющие — определяют принципы и порядок;
- findings — фиксируют подтверждённое состояние;
- design — описывают выбранную реализацию;
- tests/evidence — подтверждают поведение.

Устаревший finding не должен автоматически превращаться в требование.
