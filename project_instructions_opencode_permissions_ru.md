# Инструкции проекта OpenCode Permissions

Проект посвящён исследованию и разработке более автономного и осмысленного режима разрешений действий OpenCode.

Главный управляющий документ проекта:

`opencode_permissions_project_master_ru.md`

Перед содержательной работой обязательно прочитай его целиком. Он определяет цель, границы, порядок работ, критерии приёмки и приоритет источников. Если текущая задача противоречит ему, сначала укажи противоречие.

Дополнительный документ с подтверждёнными фактами, рабочими гипотезами и открытыми вопросами:

`opencode_permissions_findings_ru.md`

Его использовать как handoff-контекст, но не как нормативный источник. Findings могут устаревать и должны перепроверяться.

## Источники истины

Приоритет источников:

1. Фактическое поведение установленной версии OpenCode и её локальная конфигурация.
2. Актуальная официальная документация OpenCode.
3. `opencode_permissions_project_master_ru.md`.
4. Репозиторий `agent-safe` как архитектурный образец безопасной автоматизации.
5. `opencode_permissions_findings_ru.md` как накопленные наблюдения и гипотезы.

Не переносить настройки из `agent-safe` механически. Использовать его принципы: короткие правила для агента, технические permissions, отдельные процедуры и обязательный runtime-предохранитель для опасных действий.

## Основная цель

Сократить ручные подтверждения OpenCode до минимально необходимого числа, не превращая систему в безусловное автоматическое разрешение любых команд.

Целевой штатный режим:

- чтение, поиск, безопасная диагностика, сборка и тесты идут без участия пользователя;
- агент самостоятельно повторяет обычный цикл исправления и проверки;
- опасные операции блокируются технически;
- неоднозначные операции анализируются автоматически;
- пользователь привлекается только при реальной неоднозначности или значимом изменении внешнего состояния;
- при запросе пользователю показывается понятное описание последствий, а не длинная строка команды.

## Рабочий подход

Сначала исследовать фактическую версию и текущие запросы разрешений. Не начинать с широкого `"bash": "allow"` или `--auto`.

Для каждой проблемы разделять:

- что можно решить штатным `opencode.json`;
- что требует более точных правил;
- что требует разбора команды;
- что удобнее вынести в custom tool или plugin;
- где полезна дополнительная модель-аудитор;
- где должен остаться пользователь.

Предпочитать технические ограничения промптовым запретам.

## Модель принятия решения

Рассматривать архитектуру из четырёх уровней:

1. Детерминированный `ALLOW` для простых и проверенных операций.
2. Детерминированный `DENY` для явно разрушительных операций.
3. Автоматический анализ неоднозначных операций, при необходимости с небольшой моделью-аудитором.
4. `ASK_USER` только для остаточной неопределённости.

Модель-аудитор не должна иметь права отменять жёсткий `DENY`.

## Требования к подтверждению пользователя

Если подтверждение всё же требуется, основной текст должен объяснять:

- цель действия;
- что именно будет сделано;
- где это произойдёт;
- какие объекты будут изменены;
- основной риск;
- обратимость;
- почему система не решила автоматически;
- рекомендацию проверяющего слоя.

Сырая команда должна быть доступна как техническая подробность, но не должна быть единственным объяснением.

При невозможности достоверно объяснить длинную составную команду предложить разбить её на более простые атомарные действия.

## Особые случаи

Отдельно исследовать:

- `find` с `-delete`, `-exec`, `-execdir`, `-ok`;
- конвейеры и `xargs`;
- `cmd /c`, PowerShell, Python и другие способы вложенного выполнения;
- `ssh_relay` и полный разбор удалённой команды;
- составные команды `&&`, `||`, `;`, конвейеры и перенаправления;
- доступ к соседним и внешним каталогам;
- секретные файлы;
- постоянные правила, создаваемые через `always`;
- режим `--auto`.

Не считать безопасной команду только по первому исполняемому файлу или префиксу строки.

## Образец agent-safe

Использовать `agent-safe` как образец разделения ответственности:

- `AGENTS.md` — короткие правила поведения;
- `opencode.json` — технические `allow/ask/deny`;
- skills — подробные процедуры, загружаемые по необходимости;
- `safe` CLI — runtime-протокол для рискованных действий;
- dry-run, backup и rollback перед изменением конфигурации;
- Recovery Mode после неожиданного результата.

Не дублировать длинные правила во всех слоях.

## Безопасность исследования

Не проверять опасные правила реальными разрушительными командами.

Для отрицательных тестов использовать dry-run, временные каталоги, фиктивные команды, mock/custom tool, parser-only режим и анализ решения без исполнения.

Запрещено для эксперимента намеренно удалять рабочие файлы, сбрасывать Git, перезапускать production-службы, менять MongoDB, секреты или рабочие системные настройки.

## Правила разработки

Перед изменением конфигурации или кода:

1. Зафиксировать текущую версию OpenCode.
2. Найти действующие конфигурационные файлы и порядок их наложения.
3. Сохранить исходное состояние.
4. Сначала показать предлагаемый diff.
5. Иметь способ отката.
6. После изменения провести положительные и отрицательные проверки.
7. Зафиксировать, какие подтверждения исчезли и какие остались.

Если фактическое поведение отличается от документации, приоритет имеет воспроизводимый эксперимент на установленной версии; расхождение обязательно занести в findings.

## Стиль результата

Отвечать по-русски, по существу, структурированно.

Разделять подтверждённые факты, выводы, гипотезы, предлагаемое решение, риски и открытые вопросы.

Не выдавать гипотезу за подтверждённое поведение OpenCode.

Для быстроменяющихся возможностей OpenCode проверять актуальную официальную документацию перед архитектурным решением.

## При завершении этапа

Возвращать:

- что исследовано;
- что подтверждено;
- что изменено;
- какие тесты выполнены;
- число оставшихся ручных подтверждений;
- новые findings;
- нерешённые риски;
- следующий рекомендуемый шаг.
